`SetCpuConfig` is a command that changes the settings the CPU firmware uses internally (the failsafe, the watchdog, PTP synchronization parameters, and so on).

:::caution
You normally do not need to change anything other than `failsafe_timeout` and `ptp_unlock_failsafe_timeout`.
Behavior is not guaranteed when any other field is changed from its default.
:::

## API

### CpuConfig

| Field                        | Type         | Default       | Description |
| ---------------------------- | ------------ | ------------- | ----------- |
| `sync_guard`                 | `Duration`   | 250 μs        | Margin for choosing the synchronization start time |
| `failsafe_timeout`           | `Option<Duration>` | `None`  | A device stops its output once nothing has arrived from the host for this long (failsafe). `None` disables the failsafe |
| `ptp_unlock_failsafe_timeout` | `Option<Duration>` | `None` | A device stops its output once it has been without its PTP lock for this long. `None` disables it |
| `fpga_bus_wait`              | `FpgaBusWait` | `Cycles3`    | Wait cycles of the bus the CPU reads and writes the FPGA through. `Cycles2` or `Cycles3` |
| `cpu_watchdog_timeout`       | `Option<Duration>` | 1 s     | Once the CPU firmware has stopped for this long, the device stops the output. `None` disables it |
| `ptp`                        | `PtpConfig`  |               | PTP synchronization parameters |

### PtpConfig

| Field                  | Type         | Default | Description |
| ---------------------- | ------------ | ------- | ----------- |
| `sync_interval`        | `Duration`   | 8 ms    | Interval at which `Sync` messages are sent |
| `tx_timestamp_timeout` | `Duration`   | 3 ms    | How long to wait for the transmit timestamp of `Delay_Req` |
| `delay_resp_timeout`   | `Duration`   | 6 ms    | How long to wait for `Delay_Resp` |
| `holdover`             | `Duration`   | 1 s     | How long the lock is kept while locked and no `Sync` arrives |
| `lock_samples`         | `NonZeroU16` | 64      | Number of consecutive samples required to lock |
| `step_threshold`       | `Duration`   | 10 μs   | The clock is stepped when the time offset exceeds this |
| `lock_threshold`       | `Duration`   | 100 ns  | Samples whose time offset is below this count toward the lock |
| `kp_milli`             | `u32`        | 50      | Proportional gain of the servo × 1000 |
| `ki_milli`             | `u32`        | 1       | Integral gain of the servo × 1000 |
| `max_freq_ppb`         | `MaxFreqPpb` | 500,000 | Limit of the frequency correction [ppb]. 0 to 2,147,483,647 |
| `delay_req_syncs`      | `NonZeroU16` | 32      | Interval at which the path delay is measured again once locked (in `Sync` messages) |
| `path_delay_filter_shift` | `PathDelayFilterShift` | 5 | Smoothing factor `1 / 2^n` of the path delay. 0 to 16. 0 disables the smoothing |
| `pause_quanta`         | `Option<NonZeroU16>` | 48 | Length of the `PAUSE` sent to the host when the link is saturated [512 bit times]. `None` sends no `PAUSE` |
| `pause_hold_syncs`     | `u16`        | 64      | Number of `Sync` messages for which a `PAUSE` keeps being sent on every send after the link was found saturated |
| `pause_retry`          | `Duration`   | 8 ms    | How long `PAUSE` keeps being sent while a `Sync` cannot be sent out |

In C#, the `Duration` fields are passed as `TimeSpan`, so they can only be specified in 100 ns units (the default 100 ns of `lock_threshold` is `TimeSpan.FromTicks(1)`).

:::danger
`failsafe_timeout` is `None` (disabled) by default, so a device keeps emitting ultrasound even when communication is lost because the host crashed or a cable was unplugged.
Set `failsafe_timeout` if the output should stop when communication is lost.
If you set it, call [`send_heartbeat()`](/autd3-sdk/en/api/basics/client/#liveness-check) periodically while there is nothing to send, and keep `failsafe_timeout` well above twice that interval. If it is too short, the output stops even while the host is running.
With `ptp_unlock_failsafe_timeout` set, a device that loses its PTP lock (any device but the first one) stops its output the same way as the failsafe once this long has passed since the loss.
Locking again takes about 1 s with the default settings, so a shorter value stops the output on every loss of the lock.

`cpu_watchdog_timeout` is how long the FPGA waits before stopping the output while the CPU firmware hangs or resets, and it stops the output the same way as the failsafe.
With `None`, a device keeps the output it had when the CPU firmware stopped.

If you close the client with `failsafe_timeout` set, the devices stop the output that long after the host goes silent.
Send [`ReleaseFailsafe`](/autd3-sdk/en/api/command/release-failsafe/) or [Clear](/autd3-sdk/en/api/command/clear/) after opening again.

An output stopped by the failsafe or the CPU watchdog does not come back automatically.
Whether a device is stopped can be checked with `is_failsafe_active()` (C#: `IsFailsafeActive`) of the `FpgaState` returned from `read_fpga_state()`.
Sending the [`ReleaseFailsafe`](/autd3-sdk/en/api/command/release-failsafe/) command resumes the output.
[Clear](/autd3-sdk/en/api/command/clear/) releases it as well, but returns every state to its default.
:::

The settings return to their defaults on [Clear](/autd3-sdk/en/api/command/clear/) and on power cycling.
Reopening the client does not reset them (the devices keep the values of the previous session), so send `Clear` to return to the defaults.
If you close the client with a PTP setting that never locks, the synchronization wait of the next open fails at `open_timeout` (`SyncTimeout`).
In that case, open with `sync_on_open` of [`TransportOption`](/autd3-sdk/en/api/basics/transport-option/) set to `false` (Rust only), send `Clear`, and open again.
From Python / C#, reboot the devices with `autd3-firmware-ota --reboot-only` or power-cycle them to return to the defaults.
