To avoid the noise of dropping the amplitude at once, `silent_stop()` first sets the [Silencer](/autd3-sdk/en/api/command/silencer/) and then drives every transducer to zero amplitude.
The Silencer setting stays overwritten, so send `SetSilencer` again before resuming the output with a different setting.

## Types of the Read Results

`read_firmware_version()` / `read_fpga_state()` / `read_telemetry()` return an array with one element per device, in device-number order.
They fail with `DeviceLost` while a device is `Lost`.

In Python, the method and field names are the same as in Rust (fields are properties).
In C#, they are PascalCase properties (`is_thermal_asserted()` → `IsThermalAsserted`, `fifo_drop` → `FifoDrop`, and so on).

### FirmwareVersion

| Member                  | Type             | Description                                            |
| ----------------------- | ---------------- | ------------------------------------------------------ |
| `cpu`                   | `Version`        | Version of the CPU firmware                            |
| `fpga`                  | `Version`        | Version of the FPGA firmware (`0.0.0` if it cannot be read) |
| `is_emulator()`         | `bool`           | Whether it is a device emulator                        |
| `is_supported()`        | `bool`           | Whether both the CPU and the FPGA are in a series this SDK supports |
| `SUPPORTED_SERIES`      | `(u8, u8)`       | Supported series (major, minor) (C#: `SupportedSeries`) |

`Version` has `major` / `minor` / `patch` (`u8`) and `is_unknown()` (whether it is `0.0.0`).

### FpgaState

| Method                    | Type             | Description                              |
| ------------------------- | ---------------- | ---------------------------------------- |
| `raw()`                   | `u8`             | Raw value of the state register          |
| `is_thermal_asserted()`   | `bool`           | Whether the thermal sensor is over the threshold |
| `current_mod_bank()`      | `ModulationBank` | Current Modulation bank                  |
| `current_pattern_bank()`  | `PatternBank`    | Current Pattern bank (shared by Pattern and STM) |
| `is_pattern_mode()`       | `bool`           | Whether a Pattern is being output        |
| `is_stm_mode()`           | `bool`           | Whether an STM is being output           |
| `is_pattern_stopped()`    | `bool`           | Whether Pattern / STM playback has stopped |
| `is_mod_stopped()`        | `bool`           | Whether Modulation playback has stopped |
| `is_transition_pending()` | `bool`           | Whether a bank switch is waiting to take effect |
| `is_failsafe_active()`    | `bool`           | Whether the output is stopped by the failsafe |

### Telemetry

CPU diagnostic counters. `Clear` resets all of them to 0 except `boot_failure` (the `Client` sends `Clear` when it opens).
Reading them does not clear them.

| Field                 | Type  | Description                                            |
| --------------------- | ----- | ------------------------------------------------------ |
| `fifo_drop`           | `u32` | Frames dropped because the receive FIFO was full       |
| `dedup`               | `u32` | Frames dropped as duplicates                           |
| `seq_mismatch`        | `u32` | Frames ignored because the sequence number did not match |
| `dispatch_error`      | `u32` | Number of times processing ended in an error           |
| `processed`           | `u32` | Frames processed                                       |
| `send_failure`        | `u32` | Number of times the NIC refused to send                |
| `failsafe`            | `u16` | Number of times the failsafe fired because communication with the host was lost |
| `ptp_unlock_failsafe` | `u16` | Number of times the failsafe fired because the PTP lock was lost |
| `sync_resync`         | `u8`  | Number of hardware resynchronizations of the sync input (reset to 0 by `Synchronize`) |
| `boot_failure`        | `u8`  | Number of steps that failed at boot (not cleared by `Clear`) |
| `cpu_watchdog`        | `u8`  | Number of times the CPU watchdog fired (kept until the FPGA is reconfigured) |

The `u32` fields wrap around to 0 on overflow, and the `u16` / `u8` fields stop at their maximum.

### BusStats

`bus_stats()` returns the host-side send/receive statistics. The values are totals since the `Client` opened, and each read gives the latest values.

| Method                       | Type  | Description                                  |
| ---------------------------- | ----- | -------------------------------------------- |
| `frames()`                   | `u64` | Frames sent                                  |
| `resets()`                   | `u64` | `Reset`s sent                                |
| `heartbeats()`               | `u64` | Heartbeats sent                              |
| `missed_heartbeat_replies()` | `u64` | Heartbeat replies that did not arrive within `reply_timeout` |
| `recoveries()`               | `u64` | Devices automatically recovered from `Lost`  |
| `acked_frames()`             | `u64` | Frames that received a reply                 |
| `worst_ack_latency_ns()`     | `u64` | Maximum time from sending to the reply [ns]  |
| `mean_ack_latency_ns()`      | `u64` | Mean time from sending to the reply [ns]     |

## ClientConfig

<CodeTabs rust={excerpt(open, "config")} python={excerpt(pyOpen, "config")} csharp={excerpt(csOpen, "config")} />

| Field                        | Type           | Default | Description                                                                         |
| ---------------------------- | -------------- | ------- | ----------------------------------------------------------------------------------- |
| `ack_timeout`                | `Duration`     | 10 ms   | Response-wait timeout. Once it elapses, the frames in flight fail with `Timeout`.   |
| `max_inflight`               | `NonZeroUsize` | `7`     | Number of frames that may be sent without waiting for a reply (for streaming sends) |
| `max_resync_rounds`          | `NonZeroU32`   | `8`     | Maximum number of attempts to get back in step with the devices                     |
| `require_supported_firmware` | `bool`         | `false` | If `true`, check on open that the firmware is supported                             |
| `resynchronize_on_recovery`  | `Option<NonZeroU32>` | `Some(3)` | Send `Synchronize` again to a device recovered from `Lost`, before the next send. The value is the maximum number of attempts; `None` sends nothing (see [State check](/autd3-sdk/en/guide/state-check/)) |
| `release_failsafe_on_recovery` | `Option<NonZeroU32>` | `Some(3)` | Send `ReleaseFailsafe` to a device recovered from `Lost`, before the next send, to resume the output stopped by the failsafe. The value is the maximum number of attempts; `None` sends nothing (see [State check](/autd3-sdk/en/guide/state-check/)) |
| `exec_lead`           | `Option<Duration>`     | `None`    | Makes every device start processing a sent frame at the same time (see below). `None` lets each device process a frame as soon as it arrives |

`max_inflight` errors if it exceeds `MAX_INFLIGHT (7)` (Python: `autd3.params.MAX_INFLIGHT`, C#: `Params.MaxInflight`).
The default is also `MAX_INFLIGHT`, which equals `DEVICE_QUEUE_FRAMES`, the number of frames in the receive queue of each device (Python: `autd3.params.DEVICE_QUEUE_FRAMES`, C#: `Params.DeviceQueueFrames`).
Setting `ack_timeout` to 0 makes opening the `Client` fail with an error (`InvalidConfig`; the `code` of the Python `Autd3Error` is `INVALID_ARGUMENT`, and the `Code` of the C# `Autd3Exception` is `InvalidArgument`).
The Python defaults are the same as in Rust, and only `resynchronize_on_recovery` / `release_failsafe_on_recovery`, whose type is an `Option`, accept `None`.

There is no retransmission. A failed command must be sent again by the user.

### exec_lead

Frames are sent to the devices one at a time, so they reach the devices at slightly different times.
With `exec_lead` set, every send carries "the current device time + `exec_lead`" rounded up to a whole microsecond, and each device holds the frame until that time.
Every device thus starts processing what one send carries at the same timing.

Note the following:
- It does not guarantee that every device always starts processing at the same time
  - If a send does not complete within `exec_lead`, a late device processes the frame after the stamped time. `exec_late` of `read_telemetry` counts how often that happened.
  - With `send_streaming`, the stamped time of a frame can come while the device is still processing the previous one; that frame is processed late (and counted in `exec_late`).
  - Even when it succeeds, only the start of the processing inside the CPU board is aligned; it does not guarantee that the start of the processing on the FPGA is aligned (that is, for example, that the phase of the emitted ultrasound is updated at the same timing)
- A send completes `exec_lead` later
- It must be at least 100 µs and shorter than 2^31 µs (about 35.8 minutes), and shorter than `lost_timeout` of [`UdpOption`](/autd3-sdk/en/api/basics/transport-option/)
- Keep `ack_timeout` (10 ms by default) longer than `exec_lead` + the processing time

## each

`each` takes a closure that receives a device and assigns a different command per device.
In Rust it is `FnMut(&Device) -> Option<C>`, in Python `Callable[[Device], Command | None]`, and in C# `Func<Device, ICommand?>`.
Nothing is assigned to a device for which `None` is returned.
