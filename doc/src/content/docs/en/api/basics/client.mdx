The `Client` connects to the devices (or the [Simulator](/autd3-sdk/en/guide/simulator/)) directly over UDP.

To continuously monitor the operating state of the devices, drive the `StateChecker` taken from `Client::state_checker` (see [State Monitoring](/autd3-sdk/en/guide/state-check/)).

## streaming

`send` waits for the response frame by frame (stop-and-wait).
To keep sending without waiting for the responses, convert the command into frames with `Frames::encode`, collect the `ResponseFuture`s that `send_frame` returns, and then await them in order.

## Liveness check

While there is nothing to send, `Client` sends nothing to the devices by itself.
If you set `failsafe_timeout` of [CpuConfig](/autd3-sdk/en/api/command/cpu-config/) (disabled by default), a device stops its output when communication from the host has been cut off for that long, so while you wait with the output kept on, call `heartbeat()` periodically to send liveness checks.
Keep the period well below half of `failsafe_timeout` (10 ms, for example). Keeping the failsafe from stopping the output is the user's responsibility.
Note that a device running an older firmware, on which `failsafe_timeout` defaulted to 500 ms, stops its output after 500 ms even if you never set it, so call `heartbeat()` there as well.

<CodeTabs rust={excerpt(methods, "heartbeat")} python={excerpt(pyMethods, "heartbeat")} csharp={excerpt(csMethods, "heartbeat")} />

`heartbeat()` sends one liveness check to every device that is not `Lost` and returns without waiting for the replies.
The replies update the [state monitoring](/autd3-sdk/en/guide/state-check/) and the device time (`device_time_now()`), so while you send nothing, a lost or rebooted device goes unnoticed and the device time estimate drifts.
It may be called concurrently with `send` and the other sends.

## Types of the Read Results

`read_firmware_version()` / `read_fpga_state()` / `read_telemetry()` return an array with one element per device, in device-number order.
They fail with `DeviceLost` while a device is `Lost`.

In Python, the method and field names are the same as in Rust (fields are properties).
In C#, they are PascalCase properties (`is_thermal_asserted()` → `IsThermalAsserted`, `fifo_drop` → `FifoDrop`, and so on).

### FirmwareVersion

| Member                  | Type             | Description                                            |
| ----------------------- | ---------------- | ------------------------------------------------------ |
| `cpu`                   | `Version`        | Version of the CPU firmware                            |
| `fpga`                  | `Version`        | Version of the FPGA firmware (`0.0.0` if it cannot be read) |
| `is_emulator()`         | `bool`           | Whether it is a device emulator                        |
| `is_supported()`        | `bool`           | Whether both the CPU and the FPGA are in a series this SDK supports |
| `SUPPORTED_SERIES`      | `(u8, u8)`       | Supported series (major, minor) (C#: `SupportedSeries`) |

`Version` has `major` / `minor` / `patch` (`u8`) and `is_unknown()` (whether it is `0.0.0`).

### Telemetry

CPU diagnostic counters. `Clear` resets all of them to 0 except `boot_failure` (the `Client` does not send `Clear` when it opens, so the values from the previous session remain).
Reading them does not clear them.

| Field                 | Type  | Description                                            |
| --------------------- | ----- | ------------------------------------------------------ |
| `fifo_drop`           | `u32` | Frames dropped because the receive FIFO was full       |
| `dedup`               | `u32` | Frames dropped as duplicates                           |
| `seq_mismatch`        | `u32` | Frames ignored because the sequence number did not match |
| `dispatch_error`      | `u32` | Number of times processing ended in an error           |
| `processed`           | `u32` | Frames processed                                       |
| `send_failure`        | `u32` | Number of times the NIC refused to send                |
| `failsafe`            | `u16` | Number of times the failsafe fired because communication with the host was lost |
| `ptp_unlock_failsafe` | `u16` | Number of times the failsafe fired because the PTP lock was lost |
| `sync_resync`         | `u8`  | Number of hardware resynchronizations of the sync input (reset to 0 by `Synchronize`) |
| `boot_failure`        | `u8`  | Number of steps that failed at boot (not cleared by `Clear`) |
| `cpu_watchdog`        | `u8`  | Number of times the CPU watchdog fired (kept until the FPGA is reconfigured) |

The `u32` fields wrap around to 0 on overflow, and the `u16` / `u8` fields stop at their maximum.

### BusStats

`bus_stats()` returns the host-side send/receive statistics. The values are totals since the `Client` opened, and each read gives the latest values.

| Method                       | Type  | Description                                  |
| ---------------------------- | ----- | -------------------------------------------- |
| `frames()`                   | `u64` | Frames sent                                  |
| `resets()`                   | `u64` | `Reset`s sent                                |
| `heartbeats()`               | `u64` | Liveness checks sent with `heartbeat()`      |
| `recoveries()`               | `u64` | Devices recovered from `Lost` by `recover()` |
| `acked_frames()`             | `u64` | Frames that received a reply                 |
| `worst_ack_latency_ns()`     | `u64` | Maximum time from sending to the reply [ns]  |
| `mean_ack_latency_ns()`      | `u64` | Mean time from sending to the reply [ns]     |

## ClientConfig

<CodeTabs rust={excerpt(open, "config")} python={excerpt(pyOpen, "config")} csharp={excerpt(csOpen, "config")} />

| Field                        | Type           | Default | Description                                                                         |
| ---------------------------- | -------------- | ------- | ----------------------------------------------------------------------------------- |
| `ack_timeout`                | `Duration`     | 10 ms   | Response-wait timeout. Once it elapses, the frames in flight fail with `Timeout`.   |
| `max_inflight`               | `NonZeroUsize` | `7`     | Number of frames that may be sent without waiting for a reply (see [streaming](#streaming)) |

`max_inflight` errors if it exceeds `MAX_INFLIGHT (7)` (Python: `autd3.params.MAX_INFLIGHT`, C#: `Params.MaxInflight`).
The default is also `MAX_INFLIGHT`, which equals `DEVICE_QUEUE_FRAMES`, the number of frames in the receive queue of each device (Python: `autd3.params.DEVICE_QUEUE_FRAMES`, C#: `Params.DeviceQueueFrames`).
Setting `ack_timeout` to 0 makes opening the `Client` fail with an error (`InvalidConfig`; the `code` of the Python `Autd3Error` is `INVALID_ARGUMENT`, and the `Code` of the C# `Autd3Exception` is `InvalidArgument`).
The Python defaults are the same as in Rust.

There is no retransmission. A failed command must be sent again by the user.
After the sends fall out of step with the devices (for example, when the responses did not arrive within `ack_timeout`), one `Reset` is sent before the next send to get back in step.
If not every device responds within `ack_timeout`, that send fails with `Timeout`, and the next send tries the `Reset` again.

## Processing time

Frames are sent to the devices one at a time, so they reach the devices at slightly different times.
Sending a frame with `send_frame_at` and an `ExecAt` stamps it with a processing time (a device time rounded up to a whole microsecond), and each device holds the frame until that time.
Every device thus starts processing what one send carries at the same timing.
`send` / `send_frame` stamp no processing time (each device processes a frame as soon as it arrives).
To send a command with a processing time, convert it into frames with `Frames::encode` and send each frame with `send_frame_at`.

<CodeTabs rust={excerpt(methods, "exec_at")} python={excerpt(pyMethods, "exec_at")} csharp={excerpt(csMethods, "exec_at")} />

| `ExecAt`         | Processing time                                                              |
| ---------------- | ---------------------------------------------------------------------------- |
| `Immediate`      | None (each device processes the frame as soon as it arrives; the same as `send_frame`) |
| `Lead(lead)`     | The current device time at the send + `lead`                                 |
| `At(sys_time)`   | The device time `sys_time` (see [SysTime](/autd3-sdk/en/api/basics/sys-time/)) |

Note the following:
- It does not guarantee that every device always starts processing at the same time
  - If sending to every device does not finish by the stamped time, a late device processes the frame after the stamped time. `exec_late` of `read_telemetry` counts how often that happened.
  - When frames are sent one after another without waiting for the responses ([streaming](#streaming)), the stamped time of a frame can come while the device is still processing the previous one; that frame is processed late (and counted in `exec_late`).
  - Even when it succeeds, only the start of the processing inside the CPU board is aligned; it does not guarantee that the start of the processing on the FPGA is aligned (that is, for example, that the phase of the emitted ultrasound is updated at the same timing)
- The response comes back after the processing, so a send completes only after the stamped time. Waiting for the response frame by frame, a command of several frames takes about the number of frames × `lead`
- `Lead` must be at least 100 µs and shorter than 2^31 µs (about 35.8 minutes), and shorter than `lost_timeout` of [`TransportOption`](/autd3-sdk/en/api/basics/transport-option/). Outside it the send fails with `InvalidPayload` and the frame is not sent
- `At` fails if it is 2^31 µs or more ahead of the current time, 2^30 µs (about 17.9 minutes) or more behind it, or `lost_timeout` or more ahead. A past time within the range is accepted; the devices process the frame at once and count it in `exec_late`
- Keep `ack_timeout` (10 ms by default) longer than the time from the send to the given time + the processing time
- `Lead` / `At` fail with `DeviceTimeUnknown` while the device time is unknown (no reply carrying it has been received yet)
- The [Simulator](/autd3-sdk/en/guide/simulator/) ignores the processing time and processes the frame at once

## each

`each` takes a closure that receives a device and assigns a different command per device.
In Rust it is `FnMut(&Device) -> Option<C>`, in Python `Callable[[Device], Command | None]`, and in C# `Func<Device, ICommand?>`.
Nothing is assigned to a device for which `None` is returned.
