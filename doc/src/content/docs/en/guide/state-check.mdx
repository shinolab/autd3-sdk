`device_status` of the [`Client`](/autd3-sdk/en/api/basics/client/) lets you monitor whether the communication with the devices is working correctly.

## Obtaining the State

`device_status` returns the state `DeviceStatus` of each device at the time of the call (`Vec<DeviceStatus>` in Rust, `list[DeviceStatus]` in Python, `DeviceStatus[]` in C#; the index is the device number).
It sends nothing to the devices and only reads the state.
`DeviceStatus` holds the following.

- `state`: the state of the device (`DeviceState`).
- `ptp_locked`: whether its PTP is locked.
- `failsafe_active`: whether it stopped its output by the failsafe and has not been released yet (whatever the cause: loss of communication with the host, loss of the PTP lock, the CPU watchdog, or a firmware update).

Aggregates such as whether every device is `Ready` or whether any is `Lost` are built from the returned values (see the example below).
`ptp_locked` and `failsafe_active` are taken from the last reply of each device, and both are `false` for a `Lost` device.
Calling it after the `Client` is closed returns an error (`Closed`, or `Network` if it closed on a communication error).

The meaning of each state is as follows.

| State     | Meaning                                                                              |
| --------- | ------------------------------------------------------------------------------------ |
| `Ready`   | The device replies, its time is synchronized, and its sync pulse is running           |
| `Syncing` | The device replies, but its time is still being synchronized or its sync pulse is not running yet |
| `Lost`    | No reply for a certain period of time                                                 |

When a device in the middle of the chain becomes `Lost`, every device beyond it also becomes `Lost`.
A `Lost` device does not come back while the `Client` is open. It stays `Lost` even if the communication comes back, for example after replugging a cable, so `close` the client and reopen it with `Client::open`.

## Detecting and Releasing the Failsafe

If `failsafe_timeout` or `ptp_unlock_failsafe_timeout` is set with [SetCpuConfig](/autd3-sdk/en/api/command/cpu-config/), a device that meets the condition stops its output (the CPU watchdog does the same).
Such a device has `failsafe_active` set, and it stays set until the device is released with [`ReleaseFailsafe`](/autd3-sdk/en/api/command/release-failsafe/) or [Clear](/autd3-sdk/en/api/command/clear/) (neither the communication coming back nor relocking releases it automatically).
Which cause stopped it can be told from the fire counts of `read_telemetry()` (`failsafe` / `ptp_unlock_failsafe` / `cpu_watchdog`).
