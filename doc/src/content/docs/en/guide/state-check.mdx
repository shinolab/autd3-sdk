The state of the devices arrives with their replies. Send a liveness check (`send_heartbeat`) or any frame, gather the replies with `collect` of the [`Client`](/autd3-sdk/en/api/basics/client/), and look at `device_status` of the `Response` to monitor whether the communication with the devices is working correctly.
`Client` itself keeps no state.

## Obtaining the State

`device_status` of a `Response` returns an array of the state `DeviceStatus` of each device at the time of the replies.

`DeviceStatus` holds the following.

- `state`: the state of the device (`DeviceState`).
- `ptp_locked`: whether its PTP is locked.
- `failsafe_active`: whether it stopped its output by the failsafe and has not been released yet

Aggregates such as whether every device is `Ready` are built from the returned values (see the example below).
`ptp_locked` and `failsafe_active` are taken from those replies.

The meaning of each `DeviceState` is as follows.

| State     | Meaning                                                    |
| --------- | ---------------------------------------------------------- |
| `Ready`   | The device replies and its time is synchronized            |
| `Syncing` | The device replies, but its time is still being synchronized |

A device that does not reply (a lost device) shows up as `collect` not returning.
`Client` does not judge a device lost: the user decides the upper bound of the wait (`tokio::time::timeout` in Rust, `asyncio.wait_for` in Python, a `CancellationToken` in C#) and whether to stop sending or to reopen when a device is lost.
When a device in the middle of the chain is lost, the devices beyond it are no longer reached either.
There is no automatic recovery. Sending on after a device is lost can make sending to every device fail, so stop sending and reopen the client with `Client::open`.
A reply from an unassigned device or with another ID (a device that rebooted, for example) is a `DeviceLost` error (which holds the number of that device).
