[`Client`](/autd3-sdk/api/basics/client/) の `device_status` を使うことでデバイスとの通信が正常に動いているかどうかを監視できる.

## 状態の取得

`device_status` は, 呼び出した時点の各デバイスの状態 `DeviceStatus` を並べて返す (Rust は `Vec<DeviceStatus>`, Python は `list[DeviceStatus]`, C# は `DeviceStatus[]`. 添字がデバイスの番号).
デバイスには何も送らず, 状態を読むだけである.
`DeviceStatus` は以下を持つ.

- `state`: デバイスの状態 (`DeviceState`).
- `ptp_locked`: PTP がロックしているか.
- `ptp_failsafe`: PTP のロックを失ったことで出力を止め, まだ解除されていないか.

全デバイスが `Ready` か, いずれかが `Lost` か, といった集約は返り値から作る (下の例を参照).
`ptp_locked` と `ptp_failsafe` はデバイスからの最後の返信の値で, `Lost` のデバイスはどちらも `false` になる.
`Client` を閉じた後に呼ぶとエラー (`Closed`. 通信エラーで閉じた場合は `Network`) になる.

状態の意味は以下の通り. 

| 状態     | 意味                                                                     |
| -------- | ------------------------------------------------------------------------ |
| `Ready`   | 返信があり, デバイスの時刻が合っていて, 同期パルスが動いている          |
| `Syncing` | 返信はあるが, 時刻を合わせている途中か, 同期パルスがまだ動いていない    |
| `Lost`    | 返信が一定時間無い                                      |

途中の 1 台が`Lost`すると, その機体より先の機体も全て `Lost` になる.
`Lost` のデバイスは `Client` を開いている間は戻らない. ケーブルの抜き差しなどで通信が戻っても `Lost` のままなので, `close` してから `Client::open` で開き直す.

## PTP failsafe の検出と解除

[SetCpuConfig](/autd3-sdk/api/command/cpu-config/) で `ptp_unlock_failsafe_timeout` を指定すると, PTP のロックを失ったまま指定の時間が経ったデバイスは出力を止める.
止まったデバイスは `ptp_failsafe` が立ち, [`ReleaseFailsafe`](/autd3-sdk/api/command/release-failsafe/) か [Clear](/autd3-sdk/api/command/clear/) で解除されるまで立ったままになる (再ロックしても自動では戻らない).

以下は, `ptp_failsafe` が立っていて再ロックした (`ptp_locked` も立っている) デバイスへ `ReleaseFailsafe` を送る例.
`send_heartbeat()` は返信を待たずに戻るので, 返信が届くまで待ってから `device_status` を呼ぶ (直後に呼ぶと, その前の返信の値が返る).
PTP failsafe は `Client` を開き直しても解除されないが, 開いた直後の `device_status` は最初の返信が届くまで `ptp_failsafe` が `false` になる.

ロックを失ったままのデバイスへ `ReleaseFailsafe` を送るとエラーになり, 出力は止まったままになる. `ptp_locked` が立つのを待ってから送る.
ホストとの通信の途絶など, PTP 以外の原因で止まった出力は `ptp_failsafe` には現れない (`read_fpga_state()` の `is_failsafe_active()` で確認する).
