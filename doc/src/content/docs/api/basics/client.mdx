デバイスの稼働状態を継続的に監視したい場合は `Client::state_checker` で取った `StateChecker` を駆動する ([状態監視](/autd3-sdk/guide/state-check/) 参照).

## streaming

`send` は 1 フレームずつ応答を待つ (stop-and-wait).
応答を待たずに続けて送るには, `Frames::encode` でコマンドをフレーム列に変換し, `send_frame` が返す `ResponseFuture` を貯めてから順に await する.

<CodeTabs rust={excerpt(sample, "streaming")} python={excerpt(pySample, "streaming")} csharp={excerpt(csSample, "streaming")} />

応答を待たずに送ってよいフレーム数は `MAX_INFLIGHT (7)` (Python: `autd3.params.MAX_INFLIGHT`, C#: `Params.MaxInflight`) で固定である.
これは各デバイスの受信キューのフレーム数 `DEVICE_QUEUE_FRAMES` (Python: `autd3.params.DEVICE_QUEUE_FRAMES`, C#: `Params.DeviceQueueFrames`) に等しい.
`MAX_INFLIGHT` 個のフレームが応答待ちの間, `send_frame` は応答が揃ってどれかが空くまで待つ.
同時に送るフレーム数をこれより少なくしたい場合は, 先に返った `ResponseFuture` を await してから次のフレームを送る.

## 生存確認

`Client` は, 送るものが無い間, 自分からはデバイスへ何も送らない.
[CpuConfig](/autd3-sdk/api/command/cpu-config/) の `failsafe_timeout` (既定は無効) を指定すると, デバイスはホストからの通信がその時間途絶えたときに出力を止めるので, 出力を保ったまま待つ間は `send_heartbeat()` を周期的に呼んで生存確認を送る.
周期は `failsafe_timeout` の半分より十分短くする (例えば 10 ms). failsafe で出力を止めないようにするのはユーザーの責任である.
なお, `failsafe_timeout` の既定が 500 ms だった旧ファームウェアのデバイスでは, 指定しなくても 500 ms で出力が止まるので, 同様に `send_heartbeat()` を呼ぶ.

<CodeTabs rust={excerpt(methods, "heartbeat")} python={excerpt(pyMethods, "heartbeat")} csharp={excerpt(csMethods, "heartbeat")} />

`send_heartbeat()` は `Lost` でない全デバイスへ生存確認を 1 回送り, 返信を待たずに返る.
返信は[状態監視](/autd3-sdk/guide/state-check/)とデバイスの時刻 (`device_time_now()`) の更新に使われるので, 送らない間はデバイスの途絶や再起動に気付けず, デバイスの時刻の推定もずれていく.
`send` などの送信と並行に呼んでもよい.

## 読み出し結果の型

`read_firmware_version()` / `read_fpga_state()` / `read_telemetry()` はデバイス番号順に 1 台 1 要素の配列を返す.
`Lost` のデバイスがある間は `DeviceLost` で失敗する.

Python のメソッド・フィールド名は Rust と同じ (フィールドはプロパティ).
C# は PascalCase のプロパティになる (`is_thermal_asserted()` → `IsThermalAsserted`, `fifo_drop` → `FifoDrop` など).

### FirmwareVersion

| メンバ                  | 型               | 説明                                                   |
| ----------------------- | ---------------- | ------------------------------------------------------ |
| `cpu`                   | `Version`        | CPU ファームウェアのバージョン                         |
| `fpga`                  | `Version`        | FPGA ファームウェアのバージョン (読めなければ `0.0.0`) |
| `is_emulator()`         | `bool`           | デバイスエミュレータか                                 |
| `is_supported()`        | `bool`           | CPU と FPGA の両方がこの SDK のサポートする系列か      |
| `SUPPORTED_SERIES`      | `(u8, u8)`       | サポートする系列 (major, minor) (C#: `SupportedSeries`) |

`Version` は `major` / `minor` / `patch` (`u8`) と `is_unknown()` (`0.0.0` か) を持つ.

### FpgaState

| メソッド                  | 型               | 説明                                     |
| ------------------------- | ---------------- | ---------------------------------------- |
| `raw()`                   | `u8`             | 状態レジスタの生の値                     |
| `is_thermal_asserted()`   | `bool`           | 温度センサが閾値を超えているか           |
| `current_mod_bank()`      | `ModulationBank` | 現在の Modulation bank                   |
| `current_pattern_bank()`  | `PatternBank`    | 現在の Pattern bank (Pattern と STM で共有) |
| `is_pattern_mode()`       | `bool`           | Pattern を出力しているか                 |
| `is_stm_mode()`           | `bool`           | STM を出力しているか                     |
| `is_pattern_stopped()`    | `bool`           | Pattern / STM の再生が止まっているか |
| `is_mod_stopped()`        | `bool`           | Modulation の再生が止まっているか |
| `is_transition_pending()` | `bool`           | bank の切り替えが発効待ちか              |
| `is_failsafe_active()`    | `bool`           | フェイルセーフで出力が止まっているか     |

### Telemetry

CPU の診断カウンタ. `Clear` で `boot_failure` 以外は 0 に戻る (`Client` は開くときに `Clear` を送らないので, 前回のセッションからの値が残る).
読み出してもクリアされない.

| フィールド            | 型    | 説明                                                   |
| --------------------- | ----- | ------------------------------------------------------ |
| `fifo_drop`           | `u32` | 受信 FIFO が満杯で捨てたフレーム数                     |
| `dedup`               | `u32` | 重複として捨てたフレーム数                             |
| `seq_mismatch`        | `u32` | シーケンス番号が合わず無視したフレーム数               |
| `dispatch_error`      | `u32` | 処理がエラーになった回数                               |
| `processed`           | `u32` | 処理したフレーム数                                     |
| `send_failure`        | `u32` | NIC が送信を断った回数                                 |
| `failsafe`            | `u16` | ホストとの通信途絶によるフェイルセーフの発火回数       |
| `ptp_unlock_failsafe` | `u16` | PTP ロック喪失によるフェイルセーフの発火回数           |
| `sync_resync`         | `u8`  | 同期入力のハード再同期回数 (`Synchronize` で 0 に戻る) |
| `boot_failure`        | `u8`  | 起動時に失敗した手順の数 (`Clear` で消えない)          |
| `cpu_watchdog`        | `u8`  | CPU ウォッチドッグの発火回数 (FPGA の再構成まで消えない) |

`u32` のフィールドは桁あふれで 0 に戻り, `u16` / `u8` のフィールドは上限で止まる.

### BusStats

`bus_stats()` はホスト側の送受信の統計を返す. 値は `Client` を開いてからの累計で, 読むたびに最新の値になる.

| メソッド                     | 型    | 説明                                         |
| ---------------------------- | ----- | -------------------------------------------- |
| `frames()`                   | `u64` | 送ったフレーム数                             |
| `resets()`                   | `u64` | 送った `Reset` の数                          |
| `heartbeats()`               | `u64` | `send_heartbeat()` で送った生存確認の数           |
| `recoveries()`               | `u64` | `recover()` で `Lost` から復帰したデバイスの数 |
| `acked_frames()`             | `u64` | 返信を受けたフレーム数                       |
| `worst_ack_latency_ns()`     | `u64` | 送信から返信までの最大時間 [ns]              |
| `mean_ack_latency_ns()`      | `u64` | 送信から返信までの平均時間 [ns]              |

## 応答待ちのタイムアウト

応答待ちのタイムアウトは [`TransportOption`](/autd3-sdk/api/basics/transport-option/) の `ack_timeout` (既定 10 ms) で, `Client` を開くときに決まり, 開いた後には変えられない.
応答待ちの先頭のフレームの応答が `ack_timeout` の間揃わなければ, 送信中のフレームはすべて `Timeout` で失敗する.

再送処理は行われない. 失敗したコマンドはユーザが送り直す必要がある.
送受信の足並みが崩れた (応答が `ack_timeout` の間揃わなかったなど) 後は, 次の送信の前に `Reset` を 1 回送って揃え直す.
全デバイスが `ack_timeout` 以内に応答しなければその送信は `Timeout` で失敗し, 次の送信がもう一度 `Reset` を試みる.

## 処理時刻

デバイスへの送信は順に 1 台ずつ行われるので, 各デバイスにフレームが届く時刻は少しずつずれる.
`send_frame_at` に `ExecAt` を渡して送ると, フレームに処理時刻 (デバイスの時刻を 1 µs 単位に切り上げたもの) が付き, 各デバイスはその時刻まで処理を待つ.
これにより, 1 回の送信の内容を全デバイスが同じタイミングで処理し始める.
`send` / `send_frame` は処理時刻を付けない (各デバイスは届いた順にすぐ処理する).
コマンドを処理時刻付きで送るには, `Frames::encode` でフレーム列に変換し, 各フレームを `send_frame_at` で送る.

<CodeTabs rust={excerpt(methods, "exec_at")} python={excerpt(pyMethods, "exec_at")} csharp={excerpt(csMethods, "exec_at")} />

| `ExecAt`         | 処理時刻                                                                 |
| ---------------- | ------------------------------------------------------------------------ |
| `Immediate`      | 付けない (届いた順にすぐ処理する. `send_frame` と同じ)                    |
| `Lead(lead)`     | 送信時のデバイスの現在時刻 + `lead`                                       |
| `At(sys_time)`   | デバイス時刻 `sys_time` ([SysTime](/autd3-sdk/api/basics/sys-time/) 参照) |

注意点は以下の通り
- 必ず全デバイスが同じ時刻に処理を始めることを保証はしない
  - 全デバイスへの送信が指定時刻までに終わらなければ, 遅れたデバイスは指定時刻を過ぎてから処理する. この回数は `read_telemetry` の `exec_late` で読める.
  - 応答を待たずに続けて送ると ([streaming](#streaming)), 前のフレームの処理中に次のフレームの指定時刻が来ることがあり, そのフレームは遅れて処理される (`exec_late` にカウントされる).
  - また, 成功したとしてもCPUボード内部の処理の開始が揃うだけであり, FPGAの処理の開始が揃うこと (すなわち, 出力される超音波の位相の更新タイミングが揃うことなど) は保証しない
- 応答は処理の後に返るので, 送信の完了は指定時刻まで遅れる. 1 フレームずつ応答を待つと, 複数フレームのコマンドはフレーム数 × `lead` 程度かかる
- `Lead` は 100 µs 以上, 2^31 µs (約 35.8 分) 未満でなければならない. また, [`TransportOption`](/autd3-sdk/api/basics/transport-option/) の `lost_timeout` 未満でなければならない. 外れると `InvalidPayload` で, そのフレームは送られない
- `At` は現在時刻より 2^31 µs 以上先・2^30 µs (約 17.9 分) 以上前, または `lost_timeout` 以上先だとエラーになる. 過ぎた時刻 (範囲内) は受け付け, デバイスはすぐに処理して `exec_late` に数える
- `ack_timeout` (既定 10 ms) は, 送信から指定時刻までの時間 + 処理時間より長くする
- `Lead` / `At` はデバイスの時刻が分からない (時刻を載せた返信をまだ受けていない) と `DeviceTimeUnknown` で失敗する
- [Simulator](/autd3-sdk/guide/simulator/) は処理時刻を無視してすぐに処理する
