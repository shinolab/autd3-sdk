`Client` は, ホストの NIC から AUTD3 のデイジーチェーンへ UDP で直接つなぐ.
通信は IPv6 のリンクローカルアドレスだけで行う. 接続の設定は `Client::open` の第 2 引数 `TransportOption` で渡す.
Link のような通信路の差し替えは無い (ハードウェア無しで試す場合は [デバイスエミュレータ](/autd3-sdk/api/connection/device-emulator/), 音場の確認は [Simulator](/autd3-sdk/guide/simulator/) を使う).

- ホストの NIC に IP アドレスを設定する必要はない (IPv6 のリンクローカルアドレスは OS が自動で付ける)
- root / 管理者権限も, npcap などの追加ドライバも要らない (普通の UDP ソケットを使う)
- Windows / Linux / macOS で動く

使う前に, ホストのファイアウォールと NIC の設定が必要になる.
[ホストのネットワーク設定](/autd3-sdk/getting-started/setup/network/) を参照すること.

| `lost_timeout`        | `Duration`  | 100 ms  | この時間返信が無いデバイスを `Lost` とする. `heartbeat` より長くする                            |
| `response_timeout`    | `Duration`  | 200 ms  | 列挙などの管理メッセージの返信を待つ時間                                                        |
| `enumeration_timeout` | `Duration`  | 30 s    | 列挙で台数がジオメトリに届くまで再試行する上限                                                  |
| `sync_timeout`        | `Duration`  | 30 s    | 時刻合わせの後, 全台がデバイス間の同期を終えて同期パルスを出し始めるまで待つ上限                |
| `send_rate_limit`     | `Option<f32>` | なし | ホストの送信が回線を占める量の上限 [%]. デバイスの回線速度 (100 Mbps) に対する割合. `None` (Python: `None`, C#: `null`) で抑えない ([回線を使い切る送り方](#回線を使い切る送り方)) |
| `send_buffer`         | `Option<NonZeroUsize>` | 8192 | ソケットの送信バッファの大きさ [B]. `None` (Python: `None`, C#: `null`) で OS の既定のままにする ([多台数へ大きなデータを送る](#多台数へ大きなデータを送る)) |
| `timer_resolution`    | `Option<Duration>`  | 1 ms    | Windows のタイマ分解能. 接続している間だけ引き上げる. `None` (Python: `None`, C#: `null`) で変更しない. 1 ms 以上. Windows 以外では何もしない |

コマンドは送る必要があるときにすぐ送られ, 各デバイスは処理を終えた時点で返信する.
一定の周期で送り続けることはなく, 送るものが無い間だけ `heartbeat` ごとに生存確認を送る.

全台の返信は, ホストにつながる 1 本の回線を順に通る.
台数が多く返信が揃わない構成では, `reply_timeout` を広げること.

### 回線を使い切る送り方

ホストからデバイスへの回線 (100 Mbps) は, デバイス間の同期のメッセージも通る.
ホストが回線を隙間なく使い切り続けると, 同期のメッセージが流れなくなる.
このときデバイスはホストの NIC に送信の一時停止 (IEEE 802.3x PAUSE) を求めて隙間を作るので, NIC のフロー制御が有効なら何もしなくてよい (多くの NIC は既定で有効).

フロー制御が効かない NIC で回線を使い切る送り方をすると, デバイスが `Syncing` になる.
その場合は `send_rate_limit` で送信を抑える. `95.0` (回線の 95 %) が目安になる.
上限を超える分は送る前に待つので, その分だけ送信が遅れる.
3.076 未満, または 100 を超える値は指定できない (開くのに失敗する).
基準はデバイス側の回線速度で, ホストの NIC のリンク速度には依らない.

### 多台数へ大きなデータを送る

台数が多いと, 1 フレームを全台へ送るだけで回線を数 ms 占める (20 台へ最大長のフレームを送ると約 2.4 ms).
ホストが回線より速く送ろうとした分は, 回線が空くまでホストの中で待つ.

`send_buffer` は, このうち OS に預けておく量の上限である.
送信バッファが埋まっている間, 送信は空くまで待つ. 回線の速さは変わらないので, 待っても全体の所要時間は延びない.

OS に預けすぎると, OS が待ちの長いデータを捨てることがある (Linux の既定の設定では, 待ちが 5 ms を超える状態が続くと捨てる).
捨てられたフレームは `Timeout` になる. 既定の 8192 はこれを避ける値で, 通常は変える必要がない.

ホストとデバイスの間にスイッチがあり, ホストが 1 Gbps でつながっている場合, 待ちはスイッチの中にできるので `send_buffer` は効かない.
その場合は `send_rate_limit` で送信を抑える.

## 接続先の自動検出

`iface` が `Auto` の場合, 同じホストの [Simulator](/autd3-sdk/guide/simulator/) と, IPv6 リンクローカルアドレスを持つ全てのインターフェースに同時に問い合わせる.
Simulator が応答すれば Simulator を, 応答しなければ AUTD3 が応答したインターフェースを使う.
2 つ以上のインターフェースで応答があった場合は, 開くのに失敗するので `Name(..)` で指定すること.

| `Interface`  | 接続先                                                              |
| ------------ | ------------------------------------------------------------------- |
| `Auto`       | Simulator が動いていれば Simulator, 動いていなければ実機             |
| `Name(..)`   | 指定した NIC につないだ実機. Simulator は見ない                      |
| `Simulator`  | Simulator のみ. 動いていなければ開くのに失敗する                     |
| `Addr(..)`   | 指定した IPv6 アドレスとポート (例: `[::1]:44336`). 応答は確かめない. [デバイスエミュレータ](/autd3-sdk/api/connection/device-emulator/) が使う |

## 開くときの処理

`Client::open` の中で, 次の処理が順に行われる (低レベルの `UdpBus::open` も同じ).

1. インターフェースの決定
1. 列挙: ホストに近い機体から順に ID (0, 1, 2, ...) を割り当てる. ID の順がジオメトリのデバイスの順になる
1. 台数の照合: 見つかった台数がジオメトリのデバイス数と一致しなければ, 開くのに失敗する
1. 時刻合わせ: ID 0 のデバイスの時刻を 0 に合わせる. 他のデバイスは ID 0 に時刻を合わせる ([デバイス間の同期](#デバイス間の同期)). 全台の同期が終わり, 同期パルスを出し始めるのを待つ

電源を入れた直後の機体は, リンクの確立に数秒かかることがある.
台数が足りない間は `enumeration_timeout` まで待って再試行する.

## 状態監視

`Client::state_checker` が返す `StateChecker` は, 各デバイスの状態を次のように報告する.

| 状態     | 意味                                                                     |
| -------- | ------------------------------------------------------------------------ |
| `Ready`   | 返信があり, ID 0 に時刻が合っていて, 同期パルスが動いている              |
| `Syncing` | 返信はあるが, 時刻を合わせている途中か, 同期パルスがまだ動いていない    |
| `Lost`    | 返信が `lost_timeout` の間無い, または機体が再起動した                  |

途中の 1 台を再起動すると, その機体より先の機体も全て `Lost` になる.
`Lost` からは自動で復帰しないので, 開き直すこと.
`Lost` の機体には何も送らなくなるので, 機体が生きていても failsafe で出力が止まる.
詳しくは [状態監視](/autd3-sdk/guide/state-check/) を参照.

## デバイス間の同期

デバイス間の時刻は, 各デバイスの Ethernet スイッチが持つ IEEE 1588 (PTP) のハードウェアタイムスタンプで揃える.
ID 0 のデバイスが基準 (grandmaster) になり, 他のデバイスはその時刻に追従する. ホスト PC は PTP に参加しないので, ホスト側の設定は要らない.

- 開くときに, 全台が ID 0 に時刻を合わせ終えるまで待つ. 合わない機体があると `sync_timeout` で失敗する
- 全台が同じ時刻を持つので, `SysTime` を使う遷移や GPIO 出力は全台で揃う
- 開いた後に時刻が合わなくなった機体は `Syncing` になり, 合い直すと `Ready` に戻る. `Syncing` が続く場合は開き直すこと

### 同期精度

4 台を数珠つなぎにした実機で, 各デバイスの GPIO 出力の立ち上がりを ID 0 と比べた結果 (2026-09-30, オシロスコープで 1 万エッジ以上).

| 出力                                         | 平均のずれ | 標準偏差 | pk-pk     |
| -------------------------------------------- | ---------- | -------- | --------- |
| `BaseSignal`                                 | 5〜32 ns   | 約 29 ns | 約 300 ns |
| `SysTimeEq` (同じ `SysTime` を全台に指定)    | 12〜20 ns  | 約 29 ns | 約 270 ns |
| `TransitionMode::SysTime` での bank 切り替え | 5〜9 ns    | 約 30 ns | 約 250 ns |

- 標準偏差と pk-pk の大半は, FPGA が同期パルスの間 (1 ms) を自分の発振器で数えることによる揺れで, デバイス間の時刻合わせの誤差ではない. パターンの連続書き込みや帯域の飽和といった負荷をかけても変わらず, 12 分の計測でドリフトは無い
- 平均のずれは, 隣り合うデバイスをつなぐリンクごとの経路の非対称 (1 リンクあたり数十 ns 以下) が積み重なったもの. ケーブルの抜き差しや電源の入れ直しでリンクが張り直されるたびに変わる (1 リンクで最大 30 ns 程度). 較正の仕組みは無い

## 制約

- 実行中の機体の抜き差しには追従しない. 検出したら開き直すこと
- デバイス間の平均のずれは, ID 0 との間にあるリンクごとの非対称が積み重なる. 4 台での最悪は約 32 ns だが, 長い鎖ではさらに大きくなりうる
- ホストとデバイスの間に L2 スイッチを挟むことは推奨しない. 挟む場合は MLD snooping を無効にすること

## エラー

通信の失敗は `Error::Network` として返る. 原因は `UdpError` で, `source()` を辿って取り出せる (Python / C# では共通の例外 `Autd3Error` / `Autd3Exception` で届き, 失敗の種類は `code` / `Code` で判別できる).
主なものは次の通り.

| `UdpError`             | 原因                                                              |
| ---------------------- | ----------------------------------------------------------------- |
| `NoInterfaceFound`     | どのインターフェースでも AUTD3 が応答しなかった                   |
| `AmbiguousInterface`   | 2 つ以上のインターフェースで応答があった. `iface` で指定する       |
| `SimulatorNotFound`    | `iface` が `Simulator` だが, Simulator が応答しなかった            |
| `DeviceCountMismatch`  | 見つかった台数がジオメトリのデバイス数と一致しない                |
| `EnumerationTimeout`   | `enumeration_timeout` までに台数がそろわなかった                   |
| `SyncTimeout`          | `sync_timeout` までに時刻が合わない, または同期パルスが動き出さない機体があった |
| `Unsent`               | フレームを OS が受け取らなかった機体があった. そのフレームは失敗するが, 接続は閉じない |
