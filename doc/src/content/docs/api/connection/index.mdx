`Client` は, ホストの NIC から AUTD3 のデイジーチェーンへ UDP で直接つなぐ.
通信は IPv6 のリンクローカルアドレスだけで行う. 接続の設定は `Client::open` の第 2 引数 `TransportOption` で渡す.
Link のような通信路の差し替えは無い (ハードウェア無しで試す場合は [デバイスエミュレータ](/autd3-sdk/api/connection/device-emulator/), 音場の確認は [Simulator](/autd3-sdk/guide/simulator/) を使う).

- ホストの NIC に IP アドレスを設定する必要はない (IPv6 のリンクローカルアドレスは OS が自動で付ける)
- root / 管理者権限も, npcap などの追加ドライバも要らない (普通の UDP ソケットを使う)
- Windows / Linux / macOS で動く

使う前に, ホストのファイアウォールと NIC の設定が必要になる.
[ホストのネットワーク設定](/autd3-sdk/getting-started/setup/network/) を参照すること.

## API

<CodeTabs rust={excerpt(sample, "api")} python={excerpt(pySample, "api")} csharp={excerpt(csSample, "api")} />

| フィールド            | 型          | 既定値  | 説明                                                                                          |
| --------------------- | ----------- | ------- | --------------------------------------------------------------------------------------------- |
| `iface`               | `Interface` | `Auto`  | デバイスをつないだ NIC. `Auto` で自動検出, `Name(..)` で名前指定                                |
| `group`               | アドレス    | なし    | 管理メッセージのマルチキャスト (`ff02::1`) の送り先を差し替える. デバイスエミュレータと Simulator 用で, 実機では使わない |
| `heartbeat`           | `Duration`  | 10 ms   | 送るものが無い間の生存確認の間隔. 250 ms 未満 (デバイスは 500 ms 途絶えると出力を止める)        |
| `reply_timeout`       | `Duration`  | 1 ms    | 生存確認の後に全台の返信を待つ上限                                                              |
| `lost_timeout`        | `Duration`  | 100 ms  | この時間返信が無いデバイスを `Lost` とする. `heartbeat` より長くする                            |
| `response_timeout`    | `Duration`  | 200 ms  | 列挙などの管理メッセージの返信を待つ時間                                                        |
| `enumeration_timeout` | `Duration`  | 10 s    | 列挙で台数がジオメトリに届くまで再試行する上限                                                  |
| `sync_timeout`        | `Duration`  | 10 s    | 時刻合わせの後, 全台がデバイス間の同期を終えて同期パルスを出し始めるまで待つ上限                |

コマンドは送る必要があるときにすぐ送られ, 各デバイスは処理を終えた時点で返信する.
一定の周期で送り続けることはなく, 送るものが無い間だけ `heartbeat` ごとに生存確認を送る.

AUTD3 は 1 台ごとに 1 フレーム分の中継遅延 (最大 1448 byte のフレームで 1 台あたり約 120 µs) がかかる.
台数が多い (十数台を超える) 構成では, `reply_timeout` を広げること.

## インターフェースの自動検出

`iface` が `Auto` の場合, IPv6 リンクローカルアドレスを持つ全てのインターフェースに問い合わせ, AUTD3 が応答したものを使う.
2 つ以上のインターフェースで応答があった場合は, 開くのに失敗するので `Name(..)` で指定すること.

## 開くときの処理

`Client::open` の中で, 次の処理が順に行われる (低レベルの `UdpBus::open` も同じ).

1. インターフェースの決定
1. 列挙: ホストに近い機体から順に ID (0, 1, 2, ...) を割り当てる. ID の順がジオメトリのデバイスの順になる
1. 台数の照合: 見つかった台数がジオメトリのデバイス数と一致しなければ, 開くのに失敗する
1. 時刻合わせ: ID 0 のデバイスにホストの時刻を送る. 他のデバイスは ID 0 に時刻を合わせる ([デバイス間の同期](#デバイス間の同期)). 全台の同期が終わり, 同期パルスを出し始めるのを待つ

電源を入れた直後の機体は, リンクの確立に数秒かかることがある.
台数が足りない間は `enumeration_timeout` まで待って再試行する.

## 状態監視

`Driver::state_checker` が返す `StateChecker` は, 各デバイスの状態を次のように報告する.

| 状態     | 意味                                                                     |
| -------- | ------------------------------------------------------------------------ |
| `Ready`   | 返信があり, ID 0 に時刻が合っていて, 同期パルスが動いている              |
| `Syncing` | 返信はあるが, 時刻を合わせている途中か, 同期パルスがまだ動いていない    |
| `Lost`    | 返信が `lost_timeout` の間無い, または機体が再起動した                  |

途中の 1 台を再起動すると, その機体より先の機体も全て `Lost` になる.
`Lost` からは自動で復帰しないので, 開き直すこと.
詳しくは [状態監視](/autd3-sdk/guide/state-check/) を参照.

## デバイス間の同期

デバイス間の時刻は, 各デバイスの Ethernet スイッチが持つ IEEE 1588 (PTP) のハードウェアタイムスタンプで揃える.
ID 0 のデバイスが基準 (grandmaster) になり, 他のデバイスはその時刻に追従する. ホスト PC は PTP に参加しないので, ホスト側の設定は要らない.

- 開くときに, 全台が ID 0 に時刻を合わせ終えるまで待つ. 合わない機体があると `sync_timeout` で失敗する
- 全台が同じ時刻を持つので, `SysTime` を使う遷移や GPIO 出力は全台で揃う
- 開いた後に時刻が合わなくなった機体は `Syncing` になり, 合い直すと `Ready` に戻る. `Syncing` が続く場合は開き直すこと

### 同期精度

4 台を数珠つなぎにした実機で, 各デバイスの GPIO 出力の立ち上がりを ID 0 と比べた結果 (2026-09-30, オシロスコープで 1 万エッジ以上).

| 出力                                   | 平均のずれ | 標準偏差 | pk-pk     |
| -------------------------------------- | ---------- | -------- | --------- |
| `BaseSignal`                           | 5〜32 ns   | 約 29 ns | 約 300 ns |
| `SysTimeEq` (同じ `SysTime` を全台に指定) | 12〜20 ns  | 約 29 ns | 約 270 ns |
| `TransitionMode::SysTime` での bank 切り替え | 5〜9 ns    | 約 30 ns | 約 250 ns |

- 標準偏差と pk-pk の大半は, FPGA が同期パルスの間 (1 ms) を自分の発振器で数えることによる揺れで, デバイス間の時刻合わせの誤差ではない. パターンの連続書き込みや帯域の飽和といった負荷をかけても変わらず, 12 分の計測でドリフトは無い
- 平均のずれは, 隣り合うデバイスをつなぐリンクごとの経路の非対称 (1 リンクあたり数十 ns 以下) が積み重なったもの. ケーブルの抜き差しや電源の入れ直しでリンクが張り直されるたびに変わる (1 リンクで最大 30 ns 程度). 較正の仕組みは無い

## 制約

- 実行中の機体の抜き差しには追従しない. 検出したら開き直すこと
- デバイス間の平均のずれは, リンクごとの非対称が台数ぶん積み重なる. 4 台での最悪は約 30 ns だが, 長い鎖ではさらに大きくなりうる
- ホストとデバイスの間に L2 スイッチを挟むことは推奨しない. 挟む場合は MLD snooping を無効にすること

## エラー

通信の失敗は `Error::Network` として返る. 原因は `UdpError` で, `source()` を辿って取り出せる (Python / C# では共通の例外で届く).
主なものは次の通り.

| `UdpError`             | 原因                                                              |
| ---------------------- | ----------------------------------------------------------------- |
| `NoInterfaceFound`     | どのインターフェースでも AUTD3 が応答しなかった                   |
| `AmbiguousInterface`   | 2 つ以上のインターフェースで応答があった. `iface` で指定する       |
| `DeviceCountMismatch`  | 見つかった台数がジオメトリのデバイス数と一致しない                |
| `EnumerationTimeout`   | `enumeration_timeout` までに台数がそろわなかった                   |
| `SyncTimeout`          | `sync_timeout` までに時刻が合わない, または同期パルスが動き出さない機体があった |
