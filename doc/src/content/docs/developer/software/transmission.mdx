[DatagramBuilder](/autd3-sdk/developer/software/datagram-builder/) が生成した `Frame` を実際にデバイスへ送り届ける処理について述べる.
実装は `crates/autd3-rs/src/client/` と `crates/autd3-rs/src/driver/` にある.

`Frames` は複数のフレームを持ち, 送信ループは `Client` ではなくユーザー側が書く.

```rust
for frame in &frames {
    client.send_checked(frame).await?;
}
```

これは 1 フレームずつ応答を待つ stop-and-wait である.
`send` を使って `ResponseFuture` を貯めれば, 応答を待たずに次を送る streaming になる.

以下ではまず stop-and-wait が 1 フレームを送り終えるまでを順に追い, そのあと streaming と障害時の処理へ進む.

## stop-and-wait

送受信は `Client` と [`Driver`](/autd3-sdk/api/basics/driver/) に分かれている.

<Mermaid
  title="Client と Driver"
  code={`flowchart LR
  U["Client (非同期)"]
  R["Driver (ユーザーが回す)"]
  D["デバイス"]
  U -- "コマンドキュー" --> R
  R -- "UDP" --> D`}
/>

`Driver` はコマンドが積まれたらすぐにデバイスへ送り, デバイスの返信を振り分けている. `Client` はそこへコマンドを積んで結果を待つ.
ライブラリはスレッドを立てないので, `Driver` をどのスレッドで回すか (あるいは async ランタイムのタスクで回すか) はユーザーが決める.
以下では, デバイス 2 台に `PerDevice` のフレームを 1 つ送る場合を例に, 送信から受信までの処理を追う.

### ① Slot を借りる

```rust
pub async fn send(&self, frame: Frame<'_>) -> Result<ResponseFuture, Error> {
    match frame.distribution() {
        Distribution::Broadcast => self.send_broadcast(&frame.datagrams()[0]).await,
        Distribution::PerDevice => self.send_datagrams(frame.datagrams()).await,
    }
}
```

`PerDevice` なので `send_datagrams` へ進む.

```rust
async fn send_datagrams(&self, datagrams: &[Datagram]) -> Result<ResponseFuture, Error> {
    if datagrams.len() != self.num_devices { /* エラー */ }
    let mut slot = self.pool.acquire().await;      // ①
    slot.reset(Distribution::PerDevice);
    for (device, datagram) in datagrams.iter().enumerate() {
        slot.set(device, datagram);
    }
    self.dispatch(slot, false).await
}
```

`Frame` は `Frames` の中身を借りているだけなので, そのまま `Driver` へ渡すことはできない.
そこで `SlotPool` から `Slot` を借り, ペイロードをそこへ写す.

```rust
struct Slot {
    dist: Distribution,
    payload: Box<[u8]>,     // num_devices * PAYLOAD_BYTES
    heads: Box<[FrameHead]>,
    status: Box<[u8]>,      // 各デバイスからの応答 (エラーコード)
    values: Box<[Value]>,   // 各デバイスからの読み出し値 (最大 32 byte)
}
```

`Slot` は送信内容と応答の両方を持つ, 1 回の送信に対応する構造体である.
`FrameHead` はデバイスごとの `Cmd` とペイロード長の組で, `payload_for` はその長さで切ったペイロードを返す.

なお, アロケーションを回避するため, `Slot` は毎回確保するのではなくプールから借りる.

```rust
pub(super) async fn acquire(&self) -> Slot {
    self.permits.acquire().await.expect("...").forget();
    self.free.lock().unwrap_or_else(PoisonError::into_inner).pop().expect("...")
}
```

`Semaphore` の許可を取ってから free list から 1 つ取り出す.
空きが無ければ `.await` で待つ.

### ② Driver へ渡す

```rust
fn dispatch(&self, slot: Slot, reply: Reply) -> Result<ResponseFuture, Error> {
    let (response_tx, response_rx) = self.completions.channel(self.mirror_for_response(), reply);
    if self.link.queue.push_cmd(CmdMessage { frame: slot, response_tx, exclusive: reply.exclusive() }).is_err() {
        return Err(Error::DriverClosed);
    }
    Ok(response_rx)
}
```

完了通知用のチャネルを 1 組作り, `Slot` と送信側 (`response_tx`) をまとめてコマンドキューへ積む.
受信側 (`response_rx`) が `ResponseFuture` としてユーザーへ返る.
コマンドキューは `Mutex<VecDeque>` に Waker を登録できるようにしたもので, 積むと待っている `Driver` (`wait` 中のスレッド, または `notified()` の future) が起きる.

ここで `send` は終わりであり, ユーザーは `ResponseFuture` を `await` して待つ.

:::note
in-flight の上限は `SlotPool` の容量 (`max_inflight`) で決まる.
キューに積めるのは `Slot` を借りられたコマンドだけなので, キューが際限なく伸びることはない.
:::

以下は `Driver` 側の処理である.

### ③ 送る

`Driver::poll` は返信を読み切ったあと `pickup` を呼び, 送ってよい枠 (窓) がある限りコマンドを取り出してすぐに送る.

```rust
fn pickup(&mut self) -> Result<(), NetworkCause> {
    /* 再送モード中や exclusive の待ちは省略 */
    while self.window_open() {                    // pending.len() < max_inflight など
        let Some(msg) = self.queue.pop_cmd() else { break };
        self.accept(msg)?;                         // exclusive なら pending が空になるまで保留
    }
    Ok(())
}

fn stage_new(&mut self, msg: CmdMessage) -> Result<(), NetworkCause> {
    let seq = self.next_seq;
    self.next_seq = self.next_seq.next();
    stage_frame(seq, &msg.frame, &mut self.bufs);
    self.pending.push_back(Inflight { seq, frame: msg.frame, acked: 0, sent_at: Instant::now(), /* .. */ });
    self.send_bufs()?;                             // UdpBus::send
    Ok(())
}
```

`stage_frame` が `Slot` の内容を送信バッファへ展開する.

```rust
fn stage_frame(seq: Seq, frame: &Slot, bufs: &mut [FrameBuf]) {
    for (device, buf) in bufs.iter_mut().enumerate() {
        buf.stage(seq, frame.cmd_for(device), frame.payload_for(device));
    }
}
```

`FrameBuf` は 1448 byte の固定長バッファと実際の長さの組で, フレームの先頭 2 byte が `Seq` と `Cmd`, 残りがペイロードである.
ペイロードは `encode` が返した長さのまま送る (末尾の 0 も省かない). デバイスはデータグラムの長さをペイロード長として扱う.
`Seq` はこの送信に割り当てられた 8 bit の通し番号で, 0 → 1 → … → 255 → 0 とラップする.

送信中のコマンドは `pending` に積まれる.

```rust
struct Inflight {
    seq: Seq,
    frame: Slot,
    acked: u128,          // ACK を返したデバイスのビットマスク
    sent_at: Instant,     // 最初に送った時刻 (統計用)
    exclusive: bool,
    response_tx: CompletionSender,
}
```

stop-and-wait では `pending` の要素は常に高々 1 つである.

### ④ 返信を待つ

送った後の `poll` は, 次に呼ぶべき期限を返す.
期限は「先頭が `ack_timeout` を過ぎる時刻」「次の生存確認の時刻」「生存確認の返信待ちの締め切り」のうち最も早いものである.
`Driver::wait` (既定の待ち方) はソケットを覗いて (読まずに) 返信が来るのを待ち, 窓に空きがあれば短い間隔 (200 µs) でコマンドキューも見る.
次の `poll` はまずソケットを非ブロッキングで読み切り, 返信を振り分ける.

```rust
while let Some(reply) = self.bus.try_recv()? {
    self.dispatch_reply(&reply)?;
}
```

返信を読み切ってからタイマ (再送・生存確認・途絶) を判定するので, `poll` の呼び出しが遅れても届いている返信を見落として誤って再送することは無い.

デバイスは各フレームの扱いを終えた時点で 1 回返信する.
FIFO モードではメインループが処理した後に, Low Latency モードでは受信割り込みの中で処理した直後に返信が届く.
返信には `ack` (最後に処理した SEQ)・`status` (そのフレームのエラーコード)・読み出し値が載る.

:::note
送るものが無い間は, `heartbeat` (既定 10 ms) ごとに `Lost` でない全デバイスへ生存確認 (`Heartbeat`) を送る.
デバイスはこれをホストが生きている信号として使い (500 ms 届かないと出力を止める), 現在の `ack` を載せて返信する.
ホストはこの返信で状態監視とデバイス時刻の観測を行う.
pending も生存確認の返信待ちも無い間は, `Driver::wait` はソケットではなくコマンドキューで待つので, 新しいコマンドが来ればすぐに起きる.
:::

### ⑤ ACK を集める

返信は 1 つずつ振り分ける.

```rust
if !not_before(reply.msg_id, self.epoch) { return; }  // Reset より前の要求への返信は捨てる
let front_seq = pending.front().seq;
let span = pending.back().seq.distance_from(front_seq) as usize;   // stop-and-wait では 0
let ack = Seq::new(reply.ack);
let ack_offset = ack.distance_from(front_seq) as usize;
if ack_offset > span { return; }                    // 窓外の ACK は無視
let bit = 1u128 << reply.device;
for entry in pending.iter_mut().take(ack_offset + 1) {
    if entry.acked & bit == 0 {
        entry.acked |= bit;
        if entry.seq == ack {
            entry.frame.record_reply(reply.device, reply.status, reply.data());
        } else {
            entry.frame.record_reply(reply.device, 0, &[]);  // 返信を取りこぼした分は結果不明
        }
    }
}
```

stop-and-wait では pending の要素は 1 つなので, `front() == back()` である.

`ack_offset` は 例えば, デバイスが一個前の SEQ を返した場合は `255` となり, `ack_offset > span` で弾かれる.

デバイス 2 台の両方が ACK を返すと, `acked` は `0b11` になる.

```
送信直後       acked = 0b00
dev1 のみ ACK  acked = 0b10
両方 ACK       acked = 0b11 = all_acked  → 完了
```

`all_acked` は全デバイスのビットが立った値である.

:::note
acked は u128 にしてある. つまり, 最大デバイス数は 128 に制限されているが特に問題ないだろう.
:::

### ⑥ 完了を通知する

```rust
while pending.front().is_some_and(|e| e.acked == all_acked) {
    let entry = pending.pop_front().expect("just checked");
    entry.response_tx.send(Ok(entry.frame.response()));
    progressed = true;
}
```

`Slot` に記録した応答を `Response` へ写して送信側へ渡す. `Slot` は `Inflight` と一緒に破棄され, プールへ戻る.
これで `Client` 側の `ResponseFuture` が起こされる.

## streaming

`send` が返す `ResponseFuture` をすぐに `await` せず貯めれば, 応答を待たずに次のフレームを送れる.
このとき `pending` に複数の `Inflight` が並ぶ.

```
pending: ┌────────┬────────┬────────┐
         │ seq=3  │ seq=4  │ seq=5  │
         │ acked  │ acked  │ acked  │
         └────────┴────────┴────────┘
          front                back
```

`stage_new` が `next_seq` を 1 つずつ配って `push_back` するので, `pending` の SEQ は連番の昇順になる.
同時に送ってよい数は `max_inflight` (既定 7) で, これはデバイスの受信キュー (FIFO) の容量に合わせてある.
FIFO モードではフレームが処理されるまでキューに残るので, これより多く送ると溢れて捨てられる (後述の再送で回復するが遅くなる).

### デバイス側の受理条件

```rust
if in_frame.seq == expected_seq {
    expected_seq = seq + 1;
    let outcome = dispatch(cmd, payload);
    set_reply(in_frame.seq, status_of(outcome), data_of(outcome));   // ack = 今処理した SEQ
} else {
    bump(Telemetry::SeqMismatch);          // 返信は現在の値のまま
}
```

デバイスは順番通りの SEQ しか受理しない.

### 累積 ACK の展開

`take(ack_offset + 1)` は, 最新の ACK に従って, 古いフレームまで遡って処理する.

```rust
for entry in pending.iter_mut().take(ack_offset + 1) { .. }
```

例として, デバイス 2 台, `pending = [seq3, seq4, seq5]` で, dev0 の返信が ack=5, dev1 の返信が ack=3 だった場合を追う.

```
front = 3, back = 5, span = 2

dev0: ack=5 → offset = 2 ≤ 2 → take(3) → seq3,4,5 に bit0 を立てる
dev1: ack=3 → offset = 0 ≤ 2 → take(1) → seq3 のみに bit1 を立てる

  [seq3: 0b11] [seq4: 0b01] [seq5: 0b01]
   ↑ 完了

pending = [seq4: 0b01] [seq5: 0b01]
```

dev1 の seq4 の返信が失われ, 次に seq5 の返信 (`ack=5`) が届くと, seq4 と seq5 の両方が一度に埋まる.
dev1 は seq4 の ACK を報告していないが, `ack=5` から遡って処理されたという扱いにする.

:::note
これが正当化されるのは, デバイスが順番通りの SEQ しか受理しないためである.
仮に dev1 が seq4 を受理していなかった場合, dev1 が seq5 を受理することはあり得ない.
:::

なお, 完了処理は `front` から順番に行うので, ユーザーから見た完了順序は送信順序と一致する.

### 窓判定

`ack_offset > span` の 比較で, 2 パターンの不正な ACK を弾いている.

| 状況 | 計算                        | 結果      |
| ---- | --------------------------- | --------- |
| 正常 | `front=3, ack=4` → `1`      | 採用      |
| 古い | `front=5, ack=4` → `255`    | 無視     |
| 異常 | `front=3, span=2, ack=9` → `6` | 無視   |

:::note
`max_inflight` は 127 (`u8::MAX` の半分) までに制限されている.
これは上の判定を破綻させないための上限である.

「古い」ACK は, 通常は `front` の 1 つ手前 (`ack_offset = 255`) に張り付く.
デバイスは順番通りの SEQ しか受理しないため, フレームを取りこぼしたデバイスの `ack` は `front - 1` でとまるからである.

問題になるのは, デバイスの `ack` が止まったまま, ホスト側の SEQ だけが先へ進んだ場合である.
例えば後述のタイムアウトで `pending` (深さ d) を一括で失敗させた後, アプリケーションが新しい SEQ で再送すると, 新しい `front` は古い `ack` の `1 + d` 先から始まる.
このときデバイス側の `ack` が古いままだと `ack_offset` は `255 - d` になる.
`max_inflight <= 127` なら `d <= 127` かつ `span <= 126` なので, `255 - d >= 128 > span` が常に成り立ち, 偽の完了通知になることはない.
:::

### exclusive

返信は「最後に処理したフレーム」の結果を運ぶので, 返信が失われて ACK が 2 つ以上飛んだ場合, 中間のエントリの結果は観測できない.

通常はこれで問題ないが, デバイスからの読み出し値を使うコマンドではこれが問題になる.

そのため, 読み出し値が必要なコマンド (例えばファームウェアのバージョンを読むコマンドなど) は, 送信中のフレームが完了するまで次のコマンドを送らないようにする.
後続が無いので, 値を運ぶ返信 (完了返信, それが失われたら再送か生存確認への返信) の `ack` は必ずそのフレームの SEQ に一致する.

## 異常系

ここまでは正常系だった.
`Driver::poll` は毎回, 次の順で処理する.

```rust
fn step(&mut self) -> Result<(), NetworkCause> {
    while let Some(reply) = self.try_recv()? {
        self.dispatch_reply(&reply)?;
    }
    let requests = self.queue.requests();
    if requests.close {
        self.shutdown(None);
        return Ok(());
    }
    /* 接続要求なら handshake を始める. handshake と Reset は poll をまたぐ状態として進む */
    self.pickup()?;
    self.check_head(Instant::now())?;       // ACK 停滞の検出と再送・Reset
    self.check_heartbeat(Instant::now())?;  // 生存確認
    Ok(())
}
```

異常は主に 2 つのパターンに分かれる.

|              | 判定                                  | 意味                                        | 担当             |
| ------------ | ------------------------------------- | ------------------------------------------- | ---------------- |
| ソケットの異常 | `send` / `recv` が `Err`              | ソケット自体の異常.                         | `shutdown`       |
| ACK 停滞     | 先頭が `ack_timeout` の間進まない      | フレーム・返信の喪失, FIFO の溢れ, デバイスの停止・途絶. | `check_head`     |

ソケットの異常は Client 側ではどうすることもできないので, `Driver` を閉じる (以後の `poll` は `Poll::Closed` を返す).

終了処理は理由 (終了要求・ソケットの異常・`Driver` の Drop) によらず `shutdown` に一本化されている.

```rust
fn shutdown(&mut self, cause: Option<NetworkCause>) {
    let (queued, connect) = self.queue.shut();
    let error = || cause.clone().map_or(Error::DriverClosed, Error::Network);
    if let Some(msg) = self.held_exclusive.take() { /* error() を返して Slot を戻す */ }
    for entry in self.pending.drain(..) { /* 同上 */ }
    for msg in queued { /* 同上 */ }
    /* UdpBus::close を呼び, Client へ閉じた原因を通知する */
}
```

`queue.shut()` はキューを閉じて, 以後の `send` をすぐに `Error::DriverClosed` で失敗させる.
`pending` / `held_exclusive` / キューに残った `CmdMessage` を掃除し, それぞれについて
待っている `ResponseFuture` にエラーを返し, `Slot` をプールへ戻す.

`shutdown`による後処理は正常系ではほぼ意味を持たない.
一方ソケットの異常では `Driver` だけが閉じ, `Client` は生き残る.
このとき後処理を怠ると, デッドロックが発生する可能性がある.
`SlotPool::acquire` は取得した `Semaphore` の許可を `forget` するため,  in-flight の `Slot` を回収しないと, プールが枯渇し以降の `send` が `acquire` で永久にブロックする可能性がある.

また, エラー種別が具体的になるというメリットもある.

### ACK 停滞

```text
   Normal
     │  先頭が ack_timeout の間進まない
     ▼
   Resync  ──── pending が空 ────▶  Normal
     │  (ack_timeout ごとに pending 全体を送り直す)
     │
     │  max_resync_rounds 回超過
     ▼
   Reset
     │  全デバイスの返信で到達を確かめ, SEQ を 0 から振り直す
     ▼
   Resync  (Reset 後)
     │  再度 max_resync_rounds 回超過
     ▼
   GiveUp  ──── 全 pending を Timeout で失敗 ────▶  Normal
```

`pending` が空になれば, どの状態からでも `Normal` へ戻る.
再送モードの間は新規コマンドを受け付けない.

既定値 (`ack_timeout = 10 ms`, `max_resync_rounds = 8`) では次のようになる.

| 経過時間     | 状態              | 出来事                                                     |
| ------------ | ----------------- | ---------------------------------------------------------- |
| 〜10 ms      | Normal            | 先頭の返信を待つ.                                          |
| 10〜80 ms    | Resync            | 10 ms ごとに pending 全体を送り直す.                       |
| 90 ms        | Resync → Reset    | `max_resync_rounds` 回送り直しても進まない. `Cmd::Reset` を送る. |
| 90〜170 ms   | Reset             | 10 ms ごとに Reset を送り直して全デバイスの返信を待つ. 揃えば SEQ を振り直して Resync へ, `max_resync_rounds` 回で揃わなければ GiveUp. |
| Reset 後 90 ms | Resync → GiveUp | Reset 済みなので今度は諦め, 全 `pending` をタイムアウトさせて `Normal` へ戻る. |

送り直しは窓全体を先頭から行う (go-back-N).
デバイスは `expected_seq` と一致するフレームだけを受理し, 既に受理したフレームは SEQ 不一致か dedup で捨てるので, 送り直しは冪等である.

#### 進捗があれば状態をリセット

1 本でも完了すれば, `rounds` と `reset_tried` が戻り, 先頭の待ち時間も数え直す.

一方で再送モードは `pending` が空になるまで維持し, 溜まっているフレームを流し切ってから通常運転へ戻る.

#### SEQ のリセット

再送を繰り返しても進まない場合, デバイスの `expected_seq` が想定外の値になっている (例えばデバイスが再起動した等) 可能性が高い.
この場合は再送では合わせられないので, `Cmd::Reset` で SEQ をリセットする.

デバイス側は `Cmd::Reset` を受けると次の状態になる.

- `expected_seq` を 0 に戻す
- `ack` を `0xFF` にする
- FIFO に積まれた未処理フレームを破棄する

`Reset` は FIFO を無視して受信割り込みの中で即座に処理され, その場で返信 (`ack = 0xFF`) が返る.

ホストは Reset を送るたびに記録した `msg_id` を使い, それ以降の `msg_id` の返信 (`ack = 0xFF`) が全デバイスから揃うまで `ack_timeout` ごとに送り直す.
揃ったら, 次に使う `msg_id` を**エポック**とし, それより前の要求への返信を以後捨てる.
Reset より前に処理されたフレームの完了返信が遅れて届いても, 振り直した SEQ 空間で誤って完了扱いにしないためである.
そのうえで `pending` の SEQ を 0 から振り直して送り直す.

```rust
fn renumber_pending(&mut self) {
    let mut seq = Seq::ZERO;
    for entry in &mut self.pending {
        entry.seq = seq;
        entry.acked = 0;
        seq = seq.next();
    }
    self.next_seq = seq;
}
```

:::note
EtherCAT 版 (Firmware v0.9.0 まで) では Reset に到達確認が無く, 決め打ちの周期数だけ送り続けていた.
UDP 版では Reset にも返信があるので, 届いたことを確かめてから振り直す.
:::

### 途絶

デバイスが返信しない (再起動・ケーブル断) 間も, 上の ACK 停滞と同じ経路で扱う.
送り直しも Reset も届かないので, 最終的に全 `pending` がタイムアウトする.
デバイスの状態は `UdpBus` が返信の途絶 (`lost_timeout`) から `Lost` と判定し, `StateChecker` が報告する.
途絶は要求を送れた機体についてだけ測る (送信そのものが失敗した機体は数えない).

`Lost` と判定した機体には, 以後 `Frame` も生存確認も送らない.
応答しない機体へ送り続けると, その宛先の近隣探索 (NDP) が解決しない間, 送ったパケットが OS の未解決キューに溜まってソケットの送信バッファを占める.
Linux の既定では 1 宛先のキューの上限 (`unres_qlen_bytes`) と送信バッファ (`wmem_default`) がどちらも 212,992 B なので, 1 台ぶんで送信バッファが尽き, 生きている機体への送信まで失敗する (実機では途中の 1 台の再起動から約 10 秒で `Driver` が閉じた).
`Lost` の機体は生きていても何も届かなくなるので, failsafe で出力が止まる.

### タイムアウト後

`fail_pending_timeout` は全 `ResponseFuture` に `Error::Timeout` を返す.
`Driver` 自体は継続し, 次のコマンドを受け付ける.

## mirror の Desync 

[DatagramBuilder](/autd3-sdk/developer/software/datagram-builder/) の `build` は「送れば適用される」前提で mirror を更新している.
送信が失敗した場合はその前提が崩れるため, mirror を `Desynced` にして以降の検証を止める必要がある.

特にタイムアウトは「適用されたかどうか自体が分からない」状態なので, 検証を続けることはできない.

この無効化は `ResponseFuture` が担う.

```rust
pub struct ResponseFuture {
    completion: Option<Arc<Completion>>,
    pool: Arc<CompletionPool>,
    mirror: Option<MirrorHandle>,
    reply: Reply,
}

impl ResponseFuture {
    fn finish(&mut self, result: Result<Response, Error>) -> Poll<Result<Response, Error>> {
        if result.is_err()
            && let Some(mirror) = self.mirror.take()
        {
            mirror.desync();
        }
        Poll::Ready(result)
    }
}
```
