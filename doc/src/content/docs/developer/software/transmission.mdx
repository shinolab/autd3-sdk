[エンコーダ](/autd3-sdk/developer/software/encoder/) が生成した `Frame` を実際にデバイスへ送り届ける処理について述べる.
実装は `crates/autd3-rs/src/client/` と `crates/autd3-rs/src/udp/` にある.

`Client` は薄いソケットである. 持つのは `Geometry`・ソケット (`Channel`)・`msg_id` の採番 (`AtomicU16`)・デバイス時刻の推定 (`DeviceClock`) だけで,
タスクを spawn せず, 返信待ちのキューもタイムアウトも途絶の判定も持たない.

`Frames` は複数のフレームを持ち, `Client::send` はそれを 1 フレームずつ送って返信を待つ.

```rust
for frame in &frames {
    client.discard_unread_replies()?;
    let msg_id = client.send_frame(frame, ExecAt::Immediate).await?;
    client.collect(msg_id).await?.check()?;
}
```

これは 1 フレームずつ応答を待つ stop-and-wait である.
`send_frame` の返す `msg_id` を `InflightFrames` に積み, 後でまとめて返信を集めれば, 応答を待たずに次を送る streaming になる.

以下ではまず stop-and-wait が 1 フレームを送り終えるまでを順に追い, そのあと streaming と障害時の処理へ進む.

## stop-and-wait

送信も受信も, それを呼んだタスクがその場で行う.

### ① 送る

```rust
let msg_id = self.last_msg_id.fetch_add(1, Ordering::Relaxed).wrapping_add(1);
for (header, datagram) in headers.iter_mut().zip(datagrams) {
    *header = FrameHeader { reserved: 0, cmd: datagram.cmd.as_u8(), exec_at: exec_at.into() };
}
for device in (0..self.channel.num_devices()).rev() {
    let index = frame.datagram_index(device);
    self.channel.send_to_device(device, Kind::Frame, msg_id, [headers[index].as_bytes(), datagrams[index].payload()]).await?;
}
```

フレームの先頭 6 byte (`FrameHeader`) が予約 (0) と `Cmd` と処理時刻 `exec_at` で, 残りがペイロードである.
`Channel` はこれに UDP のヘッダ (版数・種別・`msg_id` の 4 byte) を付け, 連結せずにベクタ I/O で 1 つのデータグラムとして送る.
`exec_at` は `ExecAt::Lead(lead)` / `ExecAt::At(t)` を渡したときだけ, それぞれ送る直前のデバイス時刻の推定値 + `lead` / `t` を µs 単位に切り上げて求め, 全デバイスに同じ値を書く (`ExecAt::Immediate` では 0).
ペイロードは `encode` が返した長さのまま送る (末尾の 0 も省かない). デバイスはデータグラムの長さをペイロード長として扱う.

`msg_id` は atomic に採番するので, `send_frame` は複数のタスクから並行に呼べる (直列化はしない).
全デバイスへ送り終えた時点で `send_frame` は `msg_id` を返して終わる. 返信は待たない.

### ② 返信を読む

返信はバックグラウンドでは読まれない. `recv` を await している間だけソケットを読む.

```rust
pub async fn recv(&self) -> Result<DeviceReply, Error> {
    let reply = self.channel.recv_from_device().await?;   // readable().await + try_recv のループ
    self.check_and_observe(&reply)?;
    Ok(reply)
}
```

`recv_from_device` はアドレス表に無い送信元・版数違い・短すぎるもの・`Frame` / `Heartbeat` 以外の返信を読み飛ばし, 1 個を `DeviceReply` にして返す.
`check_and_observe` は, ID 割り当て済みのフラグが無い・ID が送信元の機体と違う返信を `Error::DeviceLost { device }` にし (その返信は消費される. `Client` は閉じない),
ID 0 (GM) の返信に載るデバイス時刻を `DeviceClock` に入れる (ホスト側でのデバイス時刻の推定に使う).
読み出しから返すまでに await を挟まないので, `recv` を取り消しても返信は失われない.

デバイスは各フレームの扱いを終えた時点で 1 回返信する.
フレームは受信割り込みが FIFO に積み, メインループが処理した後に返信が届く.
返信には要求の `msg_id`・`status` (そのフレームのエラーコード)・状態フラグ・テレメトリ・FPGA の状態・読み出し値が載る.

:::note
生存確認 (`Heartbeat`) はユーザーが `send_heartbeat()` で送る. 1 回ごとに全デバイスへ 1 回送り, `msg_id` を返すだけで返信は待たない.
デバイスはこれをホストが生きている信号として使い (`failsafe_timeout` を指定していれば, その時間届かないと出力を止める. [フェイルセーフ](/autd3-sdk/guide/failsafe/)を参照), 現在の状態を載せて返信する.
ホストはこの返信で状態監視 (`Response::device_status()` の `state` / `ptp_locked` / `failsafe_active`) とデバイス時刻の観測を行う.
:::

### ③ 返信を集める

```rust
pub async fn collect(&self, msg_id: u16) -> Result<Response, Error> {
    let mut response = Response::for_devices(self.num_devices());
    while !response.has_all_replies() {
        let reply = self.recv().await?;
        if reply.msg_id == msg_id {
            response.record_reply(reply);                 // 同じ機体の 2 つ目は捨てる
        }
    }
    Ok(response)
}
```

`collect` は待っている `msg_id` の返信を機体ごとに記録し, 全機体が揃ったところで返す. 他の `msg_id` の返信 (遅着・`Heartbeat` への返信など) は捨てる.
`msg_id` は `u16` でラップアラウンドし, 照合は一致だけで行う (新旧の比較は持たない).
期限は持たないので, 揃わなければ返らない. 上限は呼び出し側が `tokio::time::timeout` などで付ける.
`collect` を取り消すと, それまでに読んだ返信は消費済みで失われる.

デバイス 2 台の両方が返信すると, `Response` の `replied_devices` は `0b11` になる.

```
送信直後       replied_devices = 0b00
dev1 のみ返信  replied_devices = 0b10
両方返信       replied_devices = 0b11  → 完了
```

`collect` の消費者は 1 つに限る. 並行に `recv` / `collect` すると返信を奪い合う.

読まない返信はソケットの受信バッファに溜まる. 生存確認を周期的に送りながら読まずにいると受信バッファ (Linux 既定 `rmem_default` = 212,992 B) があふれ, 以後の返信をカーネルが捨てる.
`send` と `read_*` は各フレームを送る前に `discard_unread_replies()` (非ブロッキングで読み切って捨てる) を呼んでこれを避ける. `collect` がどうせ捨てる返信なので失うものは無い.

## streaming

`send_frame` が返す `msg_id` を `InflightFrames` に積んでおけば, 応答を待たずに次のフレームを送れる.

```
InflightFrames: ┌─────────────┬─────────────┬─────────────┐
                │ msg_id=41   │ msg_id=42   │ msg_id=43   │
                └─────────────┴─────────────┴─────────────┘
```

`collect_oldest(&client)` は先頭の `msg_id` の全機体の返信が揃うまで `recv` し, 先頭を取り出して返す.
その間に読んだ, 積んである他の `msg_id` の返信はその要素に記録しておく (後の `collect_oldest` で使う). 積んでいない `msg_id` の返信と重複返信は捨てる.
await するのは `recv` だけで, 読んだ返信は返る前に記録するので, 取り消しても続きから呼び直せる.

同時に返信待ちにしてよい数は `MAX_INFLIGHT` (= 7) で, これはデバイスの受信キュー (FIFO) の容量と同じ値である.
フレームは処理されるまでキューに残るので, これより多く送ると溢れて捨てられる (返信が来ないので `collect_oldest` が返らない).
`Client` も `InflightFrames` も窓を持たないので, ユーザーが `len()` を見て `collect_oldest` してから次を送る.

### デバイス側の処理順

```rust
let Some(front) = self.fifo.front() else { return Drained::Empty };
let reply = self.handle_frame(port, header.cmd, payload);
front.reply.set(reply);
front.pop();
Drained::Completed { msg_id }   // この msg_id で返信を送る
```

メインループは受信割り込みが届いた順に FIFO へ積んだフレームを 1 つずつ取り出して処理し, 結果をそのフレームの `msg_id` を写した返信で送る.
デバイスは届いたフレームを届いた順にすべて処理する. シーケンス番号による欠落検出・順序保護・重複排除は持たない.
各フレームの返信はそのフレーム自身の結果を運び, ホストは `msg_id` でそれを対応するエントリへ届けるので,
読み出し値を使うコマンドも他のフレームと同じ窓に混ぜて送れる.

途中のフレームが欠けても, 後続のフレームはそのまま処理される.
したがって, 前のフレームの成否に依存するフレーム (Pattern の書き込みの後の bank 切替など) は, 前のフレームの返信を待ってから送る必要がある.
これは呼び出し側の責務で, `Client::send` は 1 フレームずつ返信を待つ stop-and-wait なのでこれを満たす.
streaming を組むときは, 依存のあるフレームの前で `InflightFrames` を空になるまで `collect_oldest` すること.

## 異常系

異常は主に 3 つのパターンに分かれる.

|              | 判定                                  | 意味                                        |
| ------------ | ------------------------------------- | ------------------------------------------- |
| ソケットの異常 | 受信・待機が `Err`                    | ソケット自体の異常.                         |
| 送信の失敗   | ある機体宛ての `sendto` が `Err`      | OS がその機体宛てのデータグラムを受け取らなかった. |
| 返信の停滞   | `collect` などが返らない              | フレーム・返信の喪失, FIFO の溢れ, デバイスの停止・途絶. |

### ソケットの異常

ソケットの異常は Client 側ではどうすることもできないので, `recv` / `collect` / `discard_unread_replies` は `Error::Network` を返す. `Client` を作り直すこと.

### 送信の失敗

`sendto` の結果は機体ごとに次のように扱う. `Frame` も `Heartbeat` も同じである.

| `sendto` の結果 | 扱い |
| --------------- | ---- |
| 成功 | 次の機体へ |
| ソケットが満杯 (`WouldBlock`) | `writable()` で空くまで期限なしで待ち, 送り直す |
| シグナルによる中断 (`Interrupted`) | その場で送り直す |
| それ以外のエラー (`HostUnreachable` / `NetworkDown` などの到達不能も含む) | その機体を飛ばして残りの機体へ送り続け, 送り終えた後に最初の失敗を `UdpError::Unsent { device, .. }` を原因とする `Error::Network` で返す |

1 台でも送れなかった `Frame` の `msg_id` は返らないので, そのフレームの返信は集めない (送れなかった機体にはそのフレームが届いていない).
ホストはそのフレームを自動では送り直さない. `Client` は閉じないので, 原因が解消すればそのまま送信を続けられる.

### 損失時の扱い

直結の UDP では喪失は稀なので, ホストは自動再送をしない.
フレームが 1 つ欠けても (データグラムの喪失・FIFO の溢れ), デバイスは後続のフレームをそのまま処理する.
欠けたフレームには返信が無いので, その `msg_id` の `collect` は返らない. 呼び出し側が付けた上限 (`tokio::time::timeout` など) で取り消す.

返信待ちを取り消したフレームも, デバイスに届いていれば処理されている (返信だけが失われた, 処理が上限より長い, 処理が前のフレームの待ちで遅れた).
それらへの遅着の返信は, 後の `collect` が `msg_id` の不一致で捨てる.
失敗したコマンドは呼び出し側が送り直す. ペイロードはステートレスなので同じコマンドを送り直せばよいが, デバイスは重複を排除しないので, 届いていたフレームは 2 回処理される.

:::note
`Client::open` はデバイスへフレーム (`Frame`) を送らない (handshake は無い). 列挙と ID の割当て, 時刻合わせ (`sync_on_open` が真のとき) だけを行う.
デバイスはシーケンス番号や重複排除の状態を持たないので, 前回のセッションから引き継ぐプロトコル状態は無い.
前回のセッションが送ったフレームが FIFO に残っていれば新しいセッションのフレームより先に処理されるが, その返信は新しいセッションの `collect` が待つ `msg_id` と一致しなければ捨てられる.
open は `Clear` や `Synchronize` も送らない.
:::

### 途絶

デバイスが返信しない (再起動・ケーブル断) 間, その機体を含む `collect` は返らない. `Client` は途絶を判定しないので, 上限と, 途絶とみなした後に送信を止めるか開き直すかはユーザーが決める.
再起動したデバイスは未割当に戻るので, その返信は `Error::DeviceLost { device }` になる. 途絶からは戻らないので, 戻すには開き直す.

応答しない機体へ送り続けると, その宛先の近隣探索 (NDP) が解決しない間, 送ったパケットが OS の未解決キューに溜まってソケットの送信バッファを占める.
Linux の既定では 1 宛先のキューの上限 (`unres_qlen_bytes`) と送信バッファ (`wmem_default`) がどちらも 212,992 B なので, 1 台ぶんで送信バッファが尽き, 生きている機体への送信まで止まる (実機では途中の 1 台の再起動から約 10 秒で全台への送信が失敗した).
`send_frame` はソケットが空くまで期限なしで待つので, 途絶とみなしたら送信を止めること.
1 台の途絶で残りの機体にも何も届かなくなるので, failsafe を有効にしていれば残りの機体の出力も止まる.

### 終了

`close()` は無い. `Client` を drop するとソケットが閉じる (タスクを持たないので `Drop` の実装も無い). デバイスへは何も送らず, デバイスは直前の出力を続ける.
ユーザーが spawn した生存確認のタスクなどが `Arc<Client>` を持っていれば, そのタスクを止めるまでソケットは閉じない.
