[エンコーダ](/autd3-sdk/developer/software/encoder/) が生成した `Frame` を実際にデバイスへ送り届ける処理について述べる.
実装は `crates/autd3-rs/src/client/` と `crates/autd3-rs/src/udp/` にある.

`Frames` は複数のフレームを持ち, `Client::send` はそれを 1 フレームずつ `send_frame` で送る.

```rust
for frame in &frames {
    client.send_frame(frame).await?.await?.check()?;
}
```

これは 1 フレームずつ応答を待つ stop-and-wait である.
`send_frame` の返す `ResponseFuture` を貯めれば, 応答を待たずに次を送る streaming になる (ライブラリに専用の API は無く, ユーザーがこの形で組む).

以下ではまず stop-and-wait が 1 フレームを送り終えるまでを順に追い, そのあと streaming と障害時の処理へ進む.

## stop-and-wait

送信は `send_frame` を呼んだスレッドがその場で行い, 受信は `Client` が持つ I/O スレッドが行う.

両者が共有するのは `SessionState` (返信待ちの要求の一覧 `awaiting_reply` と先頭の `ack_timeout` を数え始めた時刻など) だけである.
以下では, デバイス 2 台に `PerDevice` のフレームを 1 つ送る場合を例に, 送信から受信までの処理を追う.

### ① ReplySlot を借りる

```rust
async fn validate_and_send(&self, dist: Distribution, datagrams: &[Datagram], exec: ExecAt) -> Result<ResponseFuture, Error> {
    let _serialized = self.send_serializer.lock().await;   // send_frame どうしの直列化
    let reply_slot = self.reply_slots.acquire().await;     // ①
    /* .. */
}
```

`ReplySlot` は各デバイスからの応答 (エラーコードと読み出し値) を記録する, 1 回の送信に対応する構造体である.
アロケーションを回避するため毎回確保するのではなく `ReplySlotPool` から借りる.
`ReplySlotPool` の容量が `MAX_INFLIGHT` (= 7. 固定) なので, 空きが無ければ `.await` で待ち, in-flight 数は自然に上限へ抑えられる.

### ② 返信待ちに積む

```rust
let (tx, rx) = completion::channel();
let msg_id = self.bus.reserve_msg_id();
self.session.lock_state().push_awaiting(InflightRequest {
    msg_id,
    sent_to: None,                 // 返信を待つ機体のビットマスク
    replied_devices: 0,            // 返信を返した機体のビットマスク
    sent_at: Instant::now(),
    reply_slot,
    completion: tx,
});
```

完了通知用のチャネルを 1 組作り, 送信側 (`tx`) を `InflightRequest` の `completion` に持たせて `awaiting_reply` へ積む.
受信側 (`rx`) が `ResponseFuture` としてユーザーへ返る.
**送る前に積む**ので, 送信の途中で届いた返信も照合できる.

### ③ 送る

```rust
for (buf, datagram) in bufs.iter_mut().zip(datagrams) {
    buf.write_frame(datagram.cmd, exec_at, datagram.payload());   // [予約 (0), CMD, EXEC_AT, Payload]
}
let sent = self.bus.send(msg_id, &bufs);           // 全デバイスへ unicast. 同じ msg_id
self.apply_send_result(msg_id, sent)?;
Ok(rx)                                             // ResponseFuture
```

`FrameBuf` は 1448 byte の固定長バッファと実際の長さの組で, フレームの先頭 6 byte が予約 (0) と `Cmd` と処理時刻 `exec_at`, 残りがペイロードである.
`exec_at` は `send_frame_at` で `ExecAt::Lead(lead)` / `ExecAt::At(t)` を渡したときだけ, それぞれ送る直前のデバイス時刻の推定値 + `lead` / `t` を µs 単位に切り上げて求め, 全デバイスに同じ値を書く (`send` / `send_frame` と `ExecAt::Immediate` では 0).
ペイロードは `encode` が返した長さのまま送る (末尾の 0 も省かない). デバイスはデータグラムの長さをペイロード長として扱う.

`UdpBus::send` は `Lost` でない全デバイスへ UDP のデータグラムを `reserve_msg_id` で採った `msg_id` で送り, 実際に送った機体のビットマスクを返す.
それを `InflightRequest` の `sent_to` に記録したところで `send_frame` は終わりであり, ユーザーは `ResponseFuture` を `await` して待つ.
この時点で既に全機体の返信が届いていれば, その場で完了させる.

### ④ 返信を待つ

以下は I/O スレッドの処理である.

```rust
loop {
    self.fail_all_if_head_ack_overdue(now);   // 先頭の ack_timeout
    self.bus.take_finished_recovery(now);     // recover() の待ち窓の締め切りと, 戻った機体の通知
    let deadline = self.next_wake_deadline(now);
    match self.bus.recv(deadline) {  // ソケットの受信タイムアウトで待つ
        Ok(Some(reply)) => { self.handle_reply(&reply); self.handle_available_replies()?; }
        Ok(None) => {}
        Err(e) => return Some(NetworkCause::new(e)),
    }
}
```

期限は「先頭が `ack_timeout` を過ぎる時刻」「未返信のデバイスが `lost_timeout` に達する時刻」「`recover()` の待ち窓の締め切り (窓が開いている間)」のうち最も早いもの (どれも無ければ 1 秒後) である.
`send_heartbeat()` で送った生存確認の `lost_timeout` が I/O スレッドの起きる時刻より早いときは, `send_heartbeat()` が I/O スレッドを起こして期限を計算し直させる.
返信が 1 つ届いたら, 溜まっている返信を読み切ってからタイマの判定へ戻るので, スレッドが遅れても届いている返信を見ずに `Timeout` にすることは無い.

デバイスは各フレームの扱いを終えた時点で 1 回返信する.
フレームは受信割り込みが FIFO に積み, メインループが処理した後に返信が届く.
返信には要求の `msg_id`・`status` (そのフレームのエラーコード)・読み出し値が載る.

:::note
生存確認 (`Heartbeat`) は I/O スレッドではなくユーザーが `send_heartbeat()` で送る. 呼ぶたびに `Lost` でない全デバイスへ 1 回送り, 返信は待たない.
デバイスはこれをホストが生きている信号として使い (`failsafe_timeout` を指定していれば, その時間届かないと出力を止める), 直前に処理したフレームの結果と現在の状態を載せて返信する.
ホストはこの返信で状態監視とデバイス時刻の観測を行う. 待っている `awaiting_reply` の要求が無いので, 照合では捨てる.
:::

### ⑤ 返信を照合する

```rust
let Some(index) = state.awaiting_reply.iter().position(|r| r.msg_id == reply.msg_id) else {
    return;                                  // 待っていない返信は捨てる
};
let request = &mut state.awaiting_reply[index];
request.reply_slot.record_reply(reply.device, reply.error_code, reply.data());
request.replied_devices |= 1 << reply.device;
if !request.has_all_replies() {
    return;                                  // まだ返していない機体がある
}
```

返信は `msg_id` だけで `awaiting_reply` の要求を引く. `msg_id` は `u16` でラップアラウンドし, 照合は `awaiting_reply` にある要求との一致だけで行う (新旧の比較は持たない).
既に完了・失敗した要求への遅着の返信や `Heartbeat` への返信は, 一致する要求が無いので捨てる.

デバイス 2 台の両方が返信すると, `replied_devices` は `0b11` になる.

```
送信直後       replied_devices = 0b00
dev1 のみ返信  replied_devices = 0b10
両方返信       replied_devices = 0b11 = sent_to  → 完了
```

### ⑥ 完了を通知する

```rust
let request = state.remove_by_msg_id(reply.msg_id).expect("the request is awaiting a reply");
request.complete(&self.stats);
```

先頭の要求を外したときは, `ack_timeout` を数え始める時刻を今に更新する.
`ReplySlot` に記録した応答を `Response` へ写して送信側へ渡す. `ReplySlot` は `InflightRequest` と一緒に破棄され, プールへ戻る.
これで `Client` 側の `ResponseFuture` が起こされる.

## streaming

`send_frame` が返す `ResponseFuture` をすぐに `await` せず貯めれば, 応答を待たずに次のフレームを送れる.
このとき `awaiting_reply` に複数の `InflightRequest` が並ぶ.

```
awaiting_reply: ┌─────────────┬─────────────┬─────────────┐
                │ msg_id=41   │ msg_id=42   │ msg_id=43   │
                └─────────────┴─────────────┴─────────────┘
```

同時に送ってよい数は `MAX_INFLIGHT` (= 7) で固定で, これはデバイスの受信キュー (FIFO) の容量と同じ値である.
これより少なく抑えたい場合は, ユーザーが先に返った `ResponseFuture` を await してから次を送る.
フレームは処理されるまでキューに残るので, これより多く送ると溢れて捨てられる (返信が来ないので後述の `Timeout` になる).

### デバイス側の処理順

```rust
let Some(slot) = fifo.pop() else { return };
let outcome = dispatch(slot.cmd, slot.payload);
set_result(status_of(outcome), data_of(outcome));
```

メインループは受信割り込みが届いた順に FIFO へ積んだフレームを 1 つずつ取り出して処理し, 結果をそのフレームの `msg_id` を写した返信で送る.
デバイスは届いたフレームを届いた順にすべて処理する. シーケンス番号による欠落検出・順序保護・重複排除は持たない.
各フレームの返信はそのフレーム自身の結果を運び, ホストは `msg_id` でそれを対応するエントリへ届けるので,
読み出し値を使うコマンドも他のフレームと同じ窓に混ぜて送れる.

途中のフレームが欠けても, 後続のフレームはそのまま処理される.
したがって, 前のフレームの成否に依存するフレーム (Pattern の書き込みの後の bank 切替など) は, 前のフレームの返信を待ってから送る必要がある.
これは呼び出し側の責務で, `Client::send` は 1 フレームずつ返信を待つ stop-and-wait なのでこれを満たす.
streaming を組むときは, 依存のあるフレームの前で貯めた `ResponseFuture` を待ち切ること.

## 異常系

異常は主に 3 つのパターンに分かれる.

|              | 判定                                  | 意味                                        |
| ------------ | ------------------------------------- | ------------------------------------------- |
| ソケットの異常 | `recv` が `Err`                       | ソケット自体の異常.                         |
| 送信の失敗   | ある機体宛ての `sendto` が `Err`      | OS がその機体宛てのデータグラムを受け取らなかった. |
| 返信の停滞   | 先頭が `ack_timeout` の間進まない     | フレーム・返信の喪失, FIFO の溢れ, デバイスの停止・途絶. |

### ソケットの異常

ソケットの異常は Client 側ではどうすることもできないので, I/O スレッドは `awaiting_reply` の全要求を `Error::Network` で失敗させて終わる.
以後の `send_frame` も同じ原因の `Error::Network` を返す. `Client` を作り直すこと.

### 送信の失敗

`sendto` の結果は機体ごとに次のように扱う. どの場合も I/O スレッドは止めない.

| `sendto` の結果 | `Frame` | `Heartbeat` | `Lost` の判定 |
| --------------- | ------- | ----------- | ------------- |
| 成功 | 返信を待つ | 返信は待たない (状態監視に使う) | ソケットへ渡した時刻から未返信を数える |
| ソケットが満杯 (`WouldBlock`) | `lost_timeout` まで空きを待つ. 空かなければその機体を飛ばし (以降の機体では待たない), 送り終えた後にそのフレームを `UdpError::Unsent` を原因とする `Error::Network` で即座に失敗させる | 待たずにその機体で打ち切り, 次の `send_heartbeat()` をその機体から始める | 数えない |
| 一過性のエラー (`ConnectionReset` / `ConnectionRefused` / `HostUnreachable` / `NetworkUnreachable` / `NetworkDown` / `AddrNotAvailable` / `Interrupted`) | 送れたものとして返信を待つ. 返信が来なければ `Error::Timeout` になる | 送れたものとして扱う (返信が来なければ `lost_timeout` で `Lost`) | 送れたものとして未返信を数える |
| それ以外のエラー | そのフレームを `UdpError::Unsent` を原因とする `Error::Network` で失敗させる | その機体を飛ばして続ける | 未返信には数えない. 返信を挟まずに失敗が `lost_timeout` 続いたら `Lost` にする |

1 台でも送れなかった `Frame` は, 残りの機体が返信しても成功にしない (送れなかった機体にはそのフレームが届いていない).
ホストはそのフレームを自動では送り直さない.
`Client` は閉じないので, 原因が解消すればそのまま送信を続けられる. 解消しなければその機体は `Lost` になり, 以後は送信の対象から外れる.

### 損失時の扱い

直結の UDP では喪失は稀なので, ホストは自動再送をしない.
フレームが 1 つ欠けても (データグラムの喪失・FIFO の溢れ), デバイスは後続のフレームをそのまま処理する.
欠けたフレームには返信が無いので, `awaiting_reply` の先頭が `ack_timeout` の間進まなければ, `awaiting_reply` 全体を `Error::Timeout` で失敗させる.

```rust
fn fail_all_if_head_ack_overdue(&mut self, now: Instant) {
    if !self.is_head_ack_overdue(now) {
        return;
    }
    let (requests, timeout) = {
        let mut state = self.session.lock_state();
        (state.take_all_awaiting(), state.ack_timeout)
    };
    fail_all(requests, || Error::Timeout { timeout });
}
```

時間は送信時刻ではなく「先頭のフレームを全デバイスへ送り終えた時刻, または先頭になった時刻 (直前の先頭が完了・失敗した時刻)」の遅い方から数える.
後続のフレームが前のフレーム (`Synchronize` の latch 待ちなど) の待ち時間で道連れにならないためである.
判定の前にソケットを読み切るので, 届いている返信を見ずに `Timeout` にすることは無い.

`Error::Timeout` で失敗したフレームも, デバイスに届いていれば処理されている (返信だけが失われた, 処理が `ack_timeout` より長い, 先頭の `Timeout` の道連れになった後続).
それらへの遅着の返信は `awaiting_reply` から消えているので, `msg_id` が一致せず捨てられる.
失敗したコマンドは呼び出し側が送り直す. ペイロードはステートレスなので同じコマンドを送り直せばよいが, デバイスは重複を排除しないので, 届いていたフレームは 2 回処理される.

:::note
`Client::open` はデバイスへフレームを送らない (handshake は無い). 列挙と ID の割当て, I/O スレッドの起動だけを行う同期関数である.
デバイスはシーケンス番号や重複排除の状態を持たないので, 前回のセッションから引き継ぐプロトコル状態は無い.
前回のセッションが送ったフレームが FIFO に残っていれば新しいセッションのフレームより先に処理されるが, その返信は新しいセッションのどの `msg_id` とも一致しないので捨てられる.
open は `Clear` や `Synchronize` も送らない.
:::

### 途絶

デバイスが返信しない (再起動・ケーブル断) 間も, 上の返信の停滞と同じ経路で扱い, 最終的に `awaiting_reply` が `Timeout` する.
デバイスの状態は `UdpBus` が返信の途絶 (`lost_timeout`) から `Lost` と判定し, `StateChecker` が報告する.
途絶は要求を送れた機体についてだけ測る (送信そのものが失敗した機体は数えない).

`Lost` と判定した機体には, 以後 `Frame` も生存確認も unicast では送らない.
応答しない機体へ送り続けると, その宛先の近隣探索 (NDP) が解決しない間, 送ったパケットが OS の未解決キューに溜まってソケットの送信バッファを占める.
Linux の既定では 1 宛先のキューの上限 (`unres_qlen_bytes`) と送信バッファ (`wmem_default`) がどちらも 212,992 B なので, 1 台ぶんで送信バッファが尽き, 生きている機体への送信まで失敗する (実機では途中の 1 台の再起動から約 10 秒で全台への送信が失敗した).
`Lost` の機体は生きていても何も届かなくなるので, failsafe を有効にしていれば, ユーザが `recover()` で戻すまでの間に出力が止まる.

`Lost` の機体を待っていた要求は `Timeout` で失敗する.
以後の送信は `Lost` でない機体だけへ送り, その返信だけで完了する.

### Lost からの復帰

`Lost` の機体は, ユーザが `Client::recover()` を呼んだときだけ戻す. I/O スレッドは自分から探索しない.

`recover()` は送信と同じ `send_serializer` で直列化し, 呼び出し側のスレッドで `UdpBus::start_recovery()` を呼ぶ.
`start_recovery()` はその時点の `Lost` の機体の集合を記録して, 生存確認 (`Heartbeat`) を 1 個 `ff02::1` へ送り, 待ち窓を `recovery_reply_timeout` だけ開く (`Lost` の機体が無ければ何も送らず, 窓はすぐ閉じる).
マルチキャストは近隣探索を要さないので, 応答しない機体が居ても送信バッファを占めない.
割当済みのデバイスは `ff02::1` 宛の生存確認にも unicast のときと同じ返信を返し, 窓が開いている間, `UdpBus::recv` は `Lost` の機体のアドレスから割当済み・ID の一致する返信を受けたらその機体を戻す.
窓の外では `Lost` の機体の返信を捨てる.
再起動した機体は未割当で上がり生存確認に返信しないので, `Lost` のまま残る.

窓は `recovery_reply_timeout` が過ぎるか, 記録した `Lost` の機体が全部戻ったら閉じる.
I/O スレッドは `take_finished_recovery` でこれを見て, `recover()` の待ちを起こす.
戻った機体は `UdpBus::readmit_recovered()` が呼ばれるまで `Frame` の宛先に入らない (生存確認は届く).
`recover()` は `readmit_recovered()` で戻った機体を `Frame` の宛先へ戻し, 戻った機体を `DeviceMask` で返す.
`recover()` 自身はフレームを送らない. 返信待ちのフレームもそのままで, 各要求は送った時点の送り先の返信だけを待つ.

:::caution
探索の生存確認は届いた全デバイスが「ホストが生きている信号」として数える (unicast の生存確認と区別しない).
ただし探索は `recover()` を呼んだときの 1 回だけなので, failsafe を有効にしていれば `Lost` の間の機体は出力が止まる.
:::

`recover()` は `Synchronize` も `ReleaseFailsafe` も送らない.
戻った機体の再同期と failsafe の解除はユーザが送る ([状態監視](/autd3-sdk/guide/state-check/#lost-からの復帰) 参照).

読み出し (`read_firmware_version` / `read_fpga_state` / `read_telemetry`) は全機体ぶんの値を返すので, `Lost` の機体が居る間は `Error::DeviceLost { device }` で失敗する.
送らなかった機体の値が無いためで, 返信の `data` が短い `Error::UnexpectedReply` とは区別する.
`Response` は完了した要求の返信済みビットマスク (`replied_devices`) を持ち, 返信の無い機体のうち最も若い番号を報告する.

### 終了

`Client::close` は停止フレームを送ったあと I/O スレッドを止めて join し, `UdpBus::close` を呼ぶ.
I/O スレッドは終わるときに `awaiting_reply` の全要求を `Error::Closed` で失敗させる.
以後の `send_frame` は `Error::Closed` を返す.
